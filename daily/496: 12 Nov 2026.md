# Log 496: Keeping the Schedule

> 12 November 2026

## What I worked on

- Added recurrence state tokens on the [recurrence branch][continued], adapting
  authentication and basetime recovery to `RequestFields`. Both invoice-request
  verification paths now verify echoed state and retain `recovered_basetime`.
- Reviewed what the token authenticates: the encrypted period-zero basetime,
  offer ID, payer signing key, expected next counter, optional start offset, and
  nonce. Documented that authenticated continuity permits replay and does not
  establish whether the preceding invoice was paid.
- Split token parsing into named basetime, nonce, and HMAC slices after checking
  the total length. Preserved the layout, HMAC domain and field order,
  constant-time comparison, and checked counter increment.
- Added automatic token issuance to both invoice signing paths, using fresh
  entropy and the invoice's creation timestamp. Follow-up requests require
  previous state in this flow, counter overflow fails token creation, and the
  builder rejects state on invoices answering non-recurring requests. Manual
  responses can still omit tokens.
- Kept token support and automatic issuance in separate commits and drafted
  their messages. Formatting, diff checks, and compilation passed, including
  test code and no-std. No tests were executed and no new coverage was added;
  edits remained uncommitted for incorporation into the stack.

## Reflection

The invoice work left `recovered_basetime` visibly empty. Today gave it
something to recover. The recipient can put the period-zero basetime into an
authenticated token, send it with an invoice, and recover it when the payer echoes
that state in a later request. That lets a first-invoice anchor keep its original
starting point without storing recurrence state for each payer.

I spent some time reading what that continuity actually guarantees. Binding the
token to the offer, payer key, and expected next counter prevents those values
from being changed independently. It still permits the same request to be sent
again, and says nothing about payment of the invoice that supplied the token.
Those limits needed to be explicit in the documentation. Missing state also
remains meaningful: verification can return no recovered basetime, while a later
request with a first-invoice anchor cannot resolve its schedule without one.

Issuing the token brought the timestamp back into view. The invoice and its
next-state token have to agree on the initial basetime, so both signing paths now
use one captured time for creation. Fresh entropy belongs at issuance too. The
generic verified-request helper resolves the basetime and creates the token;
the automatic response paths decide to attach it. Keeping those responsibilities
apart leaves manual responses room to omit state without weakening the builder's
check that an attached token answers a recurring request.

The two imported commits still made sense after reading them together. One
introduces tokens and verifies them; the next starts issuing them automatically.
Most of the remaining edits made that code easier to read without changing the
cryptographic construction: named slices, shorter local bindings, and a private
verification helper. I found no concrete logic bug in the review. Compilation
covered the new plumbing, but the echoed-state behavior still needs tests.
