# Weekly Log 40: What Failure Leaves Behind

> 28 September 2026 – 05 October 2026

## Overview

The recurrence work started with a small state model: remember the active
payment and the last successful one, while `PaymentStore` keeps the payment
details. Targeted tests passed for validation failures, persisted failed
submissions, and serialization. The success path gained lookup and persistence
through the store, though incomplete manager and model pieces still blocked a
full compile.

Between those implementation passes, I worked out four proposed PR boundaries
and checked how the actual branches lined up. Returning to failure handling
then exposed something the optional active ID could not retain: once cleared,
an unsuccessful attempt looked like no attempt at all. Explicit attempt state
now keeps the failed payment visible. That change still needs behavioral tests
and deliberate handling of the persisted format.

## Highlights

### Following the payment through the store

- Kept `PaymentDetails` in `PaymentStore`, with recurrence state holding the
  payment IDs needed to follow an attempt and its last success.
- Added `PaymentSent` lookup by active payment ID and persisted the successful
  transition through the recurrence store.
- Covered validation failures and persisted failed submissions. A deterministic
  no-route case replaced a hand-built offer rejected for missing recipient
  paths.
- Passed targeted integration and serialization roundtrip tests in the earlier
  pass. Added UniFFI ID and error declarations; initiation still needs a
  binding-friendly signature.

### Finding boundaries in the actual stack

- Planned four sequential PRs: durable foundation, core payment lifecycle,
  recovery and management, then events, bindings, and documentation.
- Found that the first Foundation checkout still held the full stack; the later
  branch contained the six intended dependency, state, serialization, and
  storage commits.
- Defined eight lifecycle commits in `node-recurrence-B`, with an unrelated
  rustfmt commit still in its ancestry. The recovery and management PR still
  needs another look for size.
- Drafted the shared description around BOLT 12 and the division between
  rust-lightning protocol work and LDK Node lifecycle and management.

### Keeping a failed attempt visible

- Replaced the optional active ID in the [recurrence implementation][recurrence-branch]
  with `RecurrencePaymentState`: `NoActivePayment`, `Active(PaymentId)`, and
  `Failed(PaymentId)`. Attempt failure leaves recurrence lifecycle and paid
  count unchanged.
- Placed the enum, initialization, and success transitions in their respective
  stack commits; corrected the serialization declaration and traced an invoice
  compilation error to an unnecessary `as_ref()` and an FFI wrapper import.
- Added a terminal failure helper that persists failure only for a unique
  active-payment match and requests replay on persistence errors. Duplicate
  matches leave recurrence state untouched while ordinary failure handling
  continues in release builds.
- Passed formatting and whitespace checks for the later edits and reverted
  unrelated formatter changes. Those edits remain uncommitted, with behavioral
  tests and persisted-format compatibility still ahead.

## Reflections

I liked how little recurrence needed to remember at the start of this stretch.
The payment store already held the details, so keeping IDs was enough to follow
success without copying that data elsewhere. Failure seemed equally simple:
clear the active ID and leave the last success alone. Coming back to it on
5 October, that felt incomplete. The failed attempt had ended, but clearing the
field also erased the distinction between failure and an idle recurrence.

Keeping the failed ID gave the handler a more precise transition. It collects
the recurrences matching the active payment and updates only a unique match.
Matching the active variant keeps a replayed failure from reaching a newer
attempt, while a persistence error still asks for replay. Extracting that work
into a helper also made the duplicate case easier to hold: skipping a recurrence
update does not cut off ordinary payment failure handling in release builds.

The stack review had its own unfinished edges. A checkout name was not enough
to tell me which commits it contained, and the proposed recovery PR still felt
heavy. Giving the enum and its transitions homes in the existing stack helped
keep this later change connected to the review plan. It also left a concrete
compatibility question: replacing a persisted optional field needs care even
when the new state is easier to understand.

The earlier tests passed before this state change, so they do not settle the
new failure behavior. Next comes running that behavior, handling the persisted
format, and aligning the branches with the proposed split.
