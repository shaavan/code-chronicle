# Log 457: What Cancellation Can Ignore

> 04 September 2026

## What I worked on

- Reviewed recurring-offer cancellation against the payment window, preserving
  authentication, payer identity, recurrence continuity, and previous-state
  checks while allowing verified cancellation at any time.
- Replaced a defensive assertion for missing `recurrence_prev_state` with
  logged rejection and added coverage confirming that malformed follow-up
  requests produce neither an invoice nor an event.
- Bounded cancellation fan-out with the existing offers message request limit
  and verified that excess paths are ignored, cancellation messages have no
  reply path, and no pending payment is created.
- Moved LDK persistence-only recurrence fields to skippable odd TLV types while
  leaving BOLT wire formats unchanged, with compatibility coverage for current
  and legacy readers.
- Assigned the complete 24-commit stack’s corrections and regression coverage
  to their final commits, including the nonzero `RecurrenceLimit` documentation
  fix.

## Reflection

The review started with a small-looking question about whether cancellation should
obey the offer’s payment window. Following that check through the request flow
made the boundary plain: the window limits invoices that can be paid, while a
verified cancellation can still be recognized after it closes. That distinction
keeps cancellation from becoming an accidental payment attempt.

The defensive paths carried the same pressure. A missing
`recurrence_prev_state` was treated as impossible by an assertion, even though
the request came from outside the process. Remote input needs rejection that
survives a non-debug build. The cancellation path had another exposure: every
blinded path in an untrusted offer could produce a queued message. Reusing the
existing request limit made the bound explicit and kept cancellation from
creating payment state or reply-path obligations.

Serialization took longer to settle because two formats were easy to conflate.
The recurrence TLVs defined by BOLT stay where they are. Fields used only by LDK
persistence move to odd types so older readers can skip them, including the
always-written basetime field in reply-path context. Its default encoding stays
because the enum describes three states; optional presence would lose that
meaning.

The last pass was about placing corrections into the 24-commit stack. The
`RecurrenceLimit(0)` implementation did not need changing because zero is
outside the proposal’s valid range; its documentation did. Reading the old and
new stack side by side showed that the
[recurrence branch][recurrence-32]
now carries the cancellation hardening, downgrade-compatible persistence,
focused regression coverage, and corrected limit description. No formatter or
tests ran during this read-only review.

[recurrence-32]: https://git.rust-bitcoin.org/shaavan/rust-lightning/src/branch/recurrence-32
