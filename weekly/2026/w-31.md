# Weekly Log 31: Through the Messages

> 05 August 2026 – 07 August 2026

## Overview

This week moved between recurrence and currency review, but both threads kept
asking where a check has enough context to be honest.

The recurrence branch started with a cleanup pass that made the early commits
less provisional. Offer-side recurrence needed source hygiene, the feature
rename had to live with the feature surface instead of the tests, and the
period coverage needed calendar cases where recurrence stops being a simple
duration. Invoice-request recurrence then moved closer to the draft by using
`invreq_recurrence_prev_state`, making the field constructible through the
public API, and rejecting it from refunds.

The branch then moved into invoices. Adding the `Bolt12Invoice` recurrence
fields made the loop visible: offers describe recurrence terms, invoice
requests carry the counter and previous state, and invoices return the next
state. That made parsing feel less like three independent TLV surfaces and
more like one protocol relationship that has to be validated across messages.

The currency branch stayed with the same boundary from the previous week, but
the failures became more concrete. Static-invoice payer logic had to fail
closed when a currency amount could not be derived. Explicit invoice-request
amounts had to be checked directly instead of routed through conversion. Tiny
currency tolerance values had to survive until the final invoice amount made
them meaningful. Builder-side zero-amount rejection stayed structural rather
than pretending to prove exchange-rate support.

## Highlights

### Making recurrence less provisional

- Cleaned the offer recurrence feature commit by fixing rustdoc links, removing
  speculative source commentary, and clearing trailing whitespace.

- Moved the `offer_recurrence` rename into the feature commit where the public
  surface changes, leaving the later patch to read as coverage again.

- Added end-of-month and leap-year cases for monthly recurrence periods, where
  calendar behavior needs more than a mid-month example.

- Reworked invoice-request recurrence around
  `invreq_recurrence_prev_state`, including the draft TLV type and public
  constructor/accessor use.

- Added refund rejection coverage so invoice-request recurrence state does not
  slip into the wrong message type. ([Branch][recurrence])

### Wiring recurrence through invoices

- Added the `Bolt12Invoice` recurrence fields needed for a returned invoice to
  hand back state for the next request.

- Connected recurrence parsing across offers, invoice requests, and invoices
  instead of validating each message as a sealed local surface.

- Separated checks that belong to the message carrying a TLV from checks that
  only make sense once the surrounding recurrence context is known.

- Left the remaining pressure mostly in tests that need to pin down the
  cross-message failure cases.

### Keeping currency failures closed

- Added claim-path coverage where an unverifiable currency invoice request
  fails closed instead of being treated as acceptable.

- Replaced a reachable static-invoice payer `debug_assert` with a defensive
  `UnverifiableAmount` abandon for currency offers without a derivable
  millisatoshi amount.

- Fixed tolerance math so sub-msat per-unit currency tolerance survives until
  the final invoice amount is applied.

- Checked explicit invoice-request `amount_msats` before conversion, so a
  mutated returned invoice amount rejects as `InvalidAmount`.

- Tightened builder and parser behavior around zero currency-denominated
  offers as a structural invariant. ([Branch][currency])

## Reflections

The recurrence work made the branch feel more real this week because the
protocol stopped being a list of fields. Offers, invoice requests, and invoices
each carry their own piece, but none of those pieces explains the flow alone.
The offer tells the payer what recurrence means. The request says which
position is being asked for and echoes the previous state. The invoice returns
the next state that the following request must carry back.

That changed the shape of the parser work. Some checks are local because the
message already contains everything needed to reject a bad TLV. Refunds should
not carry invoice-request recurrence state. A public recurrence field should be
constructible through the public API. Monthly periods should behave at
end-of-month and leap-year edges. Those are direct facts.

The harder checks sit between messages. A previous state only matters because
an earlier invoice returned a next state. A counter only proves something when
it is read beside the offer terms and the invoice being requested. Pushing all
of that into local message parsing would make the code guess at context it
does not have yet. Leaving it all local would let broken recurrence sequences
pass because each individual message looked plausible enough.

The currency branch had the same pressure from the other side. Once explicit
`amount_msats` exists on the invoice request, the payer does not need a
currency converter to know whether the returned invoice changed the requested
amount. That value is already in the unit being paid. Routing it through a
null converter blurred a structural check into conversion plumbing and missed
the simpler rule.

The unverifiable static-invoice cases were a useful reminder that uncertainty
is still a result the code has to handle deliberately. A static invoice does
not carry its own invoice amount, and a currency offer without an explicit
millisatoshi request cannot be priced by that payer path. The old assertion
belonged to an older model. Returning `UnverifiableAmount` is less tidy on the
surface, but it matches the state the branch now permits.

By the end of the week, both branches were closer to the same boundary.
Structural facts get checked where the structure appears. Conversion-aware or
sequence-aware checks wait until the missing context is present. Recurrence
still needs the cross-message tests that will make the edges harder to break,
but the main loop now has a place to live.
