# Log 449: The Key Stays Inside

> 24 August 2026

## What I worked on

- Continued the recurrence stack from payer-side basetime verification into
  payer signing key derivation.
- Added `RecurrenceId` as the stable identifier LDK Node can create and
  persist for a recurring relationship.
- Introduced recurrence payer key derivation from `RecurrenceId`, `OfferId`,
  and `ExpandedKey`, keeping signing material inside LDK.
- Reworked the invoice-request builder path so it accepts a caller-provided
  payer pubkey and returns an unsigned invoice request.
- Removed `Keypair` and then `RecurrenceId` from the builder after both put
  too much flow-local state into message construction.
- Covered derivation invariants and verified that recurrence payer metadata
  can be signed with the matching derived key.

## Reflection

Today was mostly about finding the right place for a key to exist. The
recurrence flow needs a payer signing key that stays stable across requests,
but making that key easy to pass around would also make the boundary too
loose. LDK Node should be able to own the durable recurrence identifier, while
LDK owns the signing material and the derivation that turns that identifier
into a usable key.

The first implementation found the edge by stepping over it. Adding
`RecurrenceId` made sense, and the signer helper made sense, but storing a
`Keypair` in the invoice-request builder did not. Even as a private field, it
made message construction responsible for material it should only see as a
public identity. Looking back at the older payer-signing pubkey setup helped
reset the shape: the builder can derive metadata with a payer pubkey, return
an unsigned request, and leave signing to the outer flow that has the key.

There was one more tempting middle state where the builder held
`RecurrenceId` instead of the keypair. That was better, but still wrong in the
same direction. A recurrence id belongs to the node-level payment relationship,
not to the generic invoice-request builder. Keeping it out of the builder made
the new API smaller and more reusable:
`deriving_metadata_with_payer_signing_pubkey(...)` takes the identity it needs,
and `build()` returns an `UnsignedInvoiceRequest`.

Including `OfferId` in the derivation made the boundary feel less fragile.
`RecurrenceId` is stable because Node persists it, but accidental reuse across
unrelated offers should not produce the same payer pubkey. The final derivation
ties the stable recurrence relationship to the specific offer while keeping
the expanded key inside LDK's signer logic.

The tests matched that division. They check that the derived key changes when
the recurrence id or offer id changes, and that an invoice request using the
derived payer pubkey can still be signed and verified through the metadata
path. The helper has expected dead-code warnings for now because the next API
commit has not consumed it yet, but the pieces are in the right places: Node
gets a durable id, the builder gets only a pubkey, and LDK keeps the private
key material inside.
