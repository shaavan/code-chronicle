# Log 446: The Gate Holds

> 18 August 2026

## What I worked on

- Continued the recurrence branch from invoice creation into handler behavior
  for recurring invoice requests.
- Kept recurrence acceptance inside `OffersMessageFlow` instead of adding a
  recurrence-specific decision point to `ChannelManager`.
- Left cancellation requests ignored for now, with the cancellation event API
  deferred to a later slice.
- Added a defensive invariant check around previous recurrence state while
  keeping debug builds loud if verified metadata ever reaches an impossible
  branch.
- Fixed the handler tests to send recurring invoice requests through the
  offer's blinded path with recurrence present before metadata derivation.

## Reflection

Today was about deciding where the handler should know about recurrence. The
first version made that knowledge too visible. A separate
`RecurringInvreqHandling` enum gave `ChannelManager` a clear set of outcomes:
send an invoice, ignore the request, or cancel. It worked as a sketch, but it
also made the unsettled parts look more finished than they were.

Cancellation was the warning sign. Adding a
`RecurringInvoiceRequestCanceled` event made the handler feel complete for a
moment, but the API shape was not ready to carry that promise yet. Removing
the event and ignoring cancellation requests was the smaller, more honest
choice. The branch can still recognize that cancellation exists without
pretending the rest of the system already knows what durable state should be
removed.

Once cancellation stopped producing a new event, the enum mostly became
ceremony. The cleaner boundary was to let `verify_invoice_request` answer the
question it was already responsible for: whether this request should be
accepted for invoice creation. Recurrence policy now lives inside
`OffersMessageFlow`, where the request, recurrence fields, paywindow, and
metadata checks are all in view. `ChannelManager` stays on the ordinary path:
if verification returns `SendInvoice`, it builds an invoice like before.

The previous-state check was a useful place to be conservative. A follow-up
recurring request should already have valid previous state by the time it has
passed `InvoiceRequest::verify_using_metadata` or
`verify_using_recipient_data`. The extra branch in `flow.rs` should never be
hit, but it still safely rejects the request in release builds. The
`debug_assert!(false, ...)` gives debug builds a hard signal if that invariant
breaks, which feels better than quietly treating an impossible state as normal
policy.

The tests had more shape than expected. Mutating recurrence onto an offer
after construction broke metadata and blinded-path authentication, so the test
needed a builder path that includes recurrence before metadata is derived.
Sending the request directly to a node also skipped the offer-path context the
handler depends on. Once the test used the offer's blinded path and the actual
offer chain hash, the cases lined up with the behavior being promised:
in-window requests produce invoices with next state, out-of-window requests
produce nothing, and cancellation remains quiet until its own API is ready.
