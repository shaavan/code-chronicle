# Log 497: Before the Window Closes

> 14 November 2026

## What I worked on

- Added inbound recurrence timing context on the [recurrence branch][continued],
  carrying the offer's recurrence terms and invoice basetime through authenticated
  blinded payment paths. Both automatic signing paths populate them together;
  non-recurring payments leave them absent.
- Moved persistence support for the flattened recurrence types into the earlier
  offer commit. Set persisted `Requirement` discriminants to `0` for optional and
  `1` for compulsory, preserving absent defaults and the offer's wire encoding.
- Changed the timing-context helper to return `Option<(Recurrence, u64)>` and
  documented fixed and first-invoice anchors, including how manual response
  callers should populate payment paths.
- Added automatic response checks for previous state, cancellation, and the
  requested period's payment window. Centralized validation on
  `VerifiedInvoiceRequest<S>` and rechecked both invoice creation paths before
  allocating payment data, using the invoice's captured creation timestamp.
- Removed the flow-level validation wrapper and a misleading metadata-error log.
  Formatting, diff checks, documentation generation, and compilation passed,
  including test code, no-std, and fuzz where applicable. No tests were executed
  and no new coverage was added; edits remained uncommitted for incorporation
  into the stack.

## Reflection

The state token work gave later requests a way to recover their schedule. Today
carried that schedule further, into the authenticated payment context that comes
back when payment arrives. The recurrence terms and basetime need to travel
together. Returning them as one optional pair made that relationship visible,
and left ordinary payments with neither field to populate.

Persistence took a little rearranging. Adding serialization beside the new
payment context worked locally, but the recurrence types already belonged to the
offer commit. Moving their persistence support there made that earlier step
complete on its own. I also checked the optional and compulsory discriminants:
these are persisted enum values, so applying the TLV odd/even convention would
have been the wrong rule. The offer's wire format stayed as it was.

The more consequential gap appeared while reviewing automatic responses. A
request can pass its payment-window check and then wait long enough for that
window to close. Validation during verification cannot cover that wait. Both
invoice creation paths now check again before allocating payment data, using the
same time that creates the invoice, populates its timing context, and issues its
next-state token. The shared timestamp from the previous work had another job to
do. Cancellation is rejected before any payment-window calculation, and follow-up
requests still need previous state in this automatic flow.

I liked where the validation ended up. The generic verified-request type owns
the checks, the offer wrapper dispatches between variants, and the response paths
call them at the points where time matters. Removing another wrapper made those
calls easier to follow. The misleading metadata log needed to go too: an error
there does not always mean previous state was missing. Compilation covered the
plumbing, but requests waiting across a window boundary still need behavioral
coverage.
