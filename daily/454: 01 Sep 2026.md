# Log 454: Only Payment Moves It

> 01 September 2026

## What I worked on

- Re-read the recurrence handoff against the pinned rust-lightning revision
  and found that opaque recurrence state proves invoice issuance rather than
  payment completion.
- Designed a synchronous provider that lets rust-lightning validate incoming
  counters against durable paid recurrence state owned by LDK Node.
- Removed opaque state from LDK's inbound payee flow and carried the resolved
  recurrence separately through the authenticated receive payload and payment
  events.
- Preserved optional recurrence state for outbound interoperability and
  documented the remaining cancellation race and inert proportional pricing.
- Completed the handoff audit, including the initial basetime rule and the
  upstream API, boundary, quantity, atomicity, and test work still required.

## Reflection

Yesterday's Node plan exposed the public API gaps left in rust-lightning.
Today's read found a harder problem underneath them: the recurrence state
could show that an invoice had been issued, but nothing in it showed that the
invoice had been paid. A payer could leave one invoice unpaid, use its state to
request the next, and advance through the schedule without following the
payment sequence the payee expected.

The durable fact already belongs to Node, where `PaymentClaimed` is handled.
That made the provider small. rust-lightning asks for paid state using the
offer id and payer signing pubkey, then accepts only the stored next counter.
A missing record permits counter zero. Issuing an invoice leaves the record
alone; payment completion creates or advances it.

Once progression came from paid state, opaque state became unnecessary on the
inbound LDK path. The payee can issue another invoice for the same unpaid
counter without manufacturing a different continuation token. The resolved
`InvoiceRecurrence` still has to survive until payment completion, so it moves
through the authenticated blinded payload and appears separately on
`PaymentClaimable` and `PaymentClaimed`. The existing offer context does not
need to absorb recurrence-specific state.

The narrower inbound design still leaves room for other implementations.
Outbound payments preserve whether recurrence state was present or absent,
including cancellation parameters. Cancellation remains best effort: event
handling can race with another request, and deleting the paid record allows a
later counter-zero request with the same identity to look new. Writing those
limits down felt important because the small provider can otherwise look more
complete than it is.

The final read caught the first-request case as well. Counter zero has no
stored basetime, so it uses the offer's explicit base or establishes one from
the issued invoice's creation time. With that rule in place, the handoff now
describes who owns paid progress, how rust-lightning checks it, and exactly
which compromises remain before the Node implementation begins.
