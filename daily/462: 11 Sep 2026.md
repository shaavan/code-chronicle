# Log 462: At the Boundary

> 11 September 2026

## What I worked on

- Wrapped recurrence identifiers, configuration, status, payment-window, and payment-ID results in UniFFI-safe types around the existing Rust operations.
- Used the validated hexadecimal identifier pattern instead of exposing native fixed-byte IDs or internal LDK types through the binding boundary.
- Documented recurrence and payment IDs, durable acceptance, amount ceilings, manual and automatic payment, routing overrides, cancellation, and terminal removal.
- Added lifecycle replay coverage proving that the same transition reproduces identically while a later transition remains distinguishable.
- Ran default and `uniffi-default` builds, focused recurrence tests, and formatting checks with the installed Cargo toolchain.

## Reflection

The last part of this recurrence stack was mostly about deciding what could cross the UniFFI boundary without weakening the model underneath it. Native recurrence IDs are fixed byte arrays, and durable recurrence details contain LDK types that should remain internal. The existing validated hexadecimal identifier pattern gave the public API a stable representation without turning those internals into binding concerns. The same wrapping approach carried configuration, status, payment windows, and payment IDs across the boundary.

Writing the documentation exposed whether the surface actually held together. Recurrence IDs and payment IDs needed separate explanations. Durable acceptance had to be described as the point where an operation stops being an ordinary error and becomes state Node must recover. Amount ceilings, routing overrides, cancellation, and terminal removal each had to say where their authority lived and what remained after a restart. The docs were useful as a pressure test because vague boundaries became visible while trying to name them.

The final replay regression was small but important. Reprocessing one lifecycle transition must reproduce the same result, while a later transition must still advance the record. That distinction protects event consumers from both duplicate delivery and accidental suppression of real progress. Default and UniFFI builds, focused tests, and formatting passed. The pinned Cargo 1.75 toolchain still could not parse the lockfile version, so verification used the installed Cargo version without changing the lockfile.

The stack now contains its planned recurrence foundation through [the recurrence branch][recurrence-01]. It still leaves hardening work: resubmitting missing prepared attempts during recovery, atomically claiming work between manual and automatic payment, scheduling by exact due time, tracking every cancellation-delivery outcome, and applying all recurrence configuration before the first external LDK action. Recording those limits beside the completed behavior felt more accurate than letting a finished API imply that every recovery edge was already solved.
