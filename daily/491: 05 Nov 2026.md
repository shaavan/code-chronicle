## Reflection

I returned to static-invoice refreshes today. Refreshing after a channel closes
or forwarding parameters change keeps async payments from using stale blinded
paths. The awkward part was how easily a counterparty could keep asking for
that work. Alternating its fees could repeatedly send us through invoice
construction, signing, and outbound messages.

My first thought was to allow a fixed number of immediate refreshes before
waiting for the timer. Reading the branch showed why the allowance belonged
to each channel. With a shared budget, one noisy channel could spend it and
leave an honest channel waiting. Giving each channel its first refresh between
ticks preserved that response, while combining further changes on the same
channel into one refresh. The limit is still partial: immediate work grows
with the number of distinct channels updated, and peer and channel collection
still happens before the throttle check.

The existing tests covered the first changed update, an unchanged replay, and
closure, including reuse of the server's storage slots. They left the repeated
changes and timer behavior unexercised. I expanded the update test, then found
myself having to decode loop indexes to understand which stage I was reading.
Pulling the invoice checks into a helper helped, but I still preferred spelling
out the sequence: refresh once, ignore the replay, defer three more changes,
tick once, then prove another change can refresh immediately. A final tick
checks that no deferred refresh remains.

That explicit version made the earlier loop redundant. I liked being able to
read the allowance being spent and restored without keeping an index in my
head. The PR update now explains why another channel should retain its own
immediate refresh. The regression coverage expresses that timer behavior more
directly too, though I have not run the tests yet.
