# Log 444: State Without Memory

> 15 August 2026

## What I worked on

- Picked up the recurrence branch after the first reviewable protocol slice was
  already separated.
- Scoped `invoice_recurrence_next_state` work to internal creation and
  verification plumbing.
- Kept recurrence state stateless by tying the token to the offer, payer,
  counter, start, and key material instead of stored payee-side state.
- Left public payer APIs, cancellation behavior, proportional amount policy,
  and ChannelManager response handling outside the state-token commit.
- Added direct recurrence state-token validation tests for success, mismatched
  inputs, malformed state, and overflow behavior.

## Reflection

Today was about adding the next piece without letting it pull the whole
recurrence design along with it. The first PR already had the message shape in
place: offers could describe recurrence, invoice requests could carry the
counter and previous state, and invoices could expose recurrence fields. That
left the more awkward question behind the field wiring. If the invoice gives
the payer a next-state value, what exactly is rust-lightning promising about
that value?

The useful answer was smaller than a full recurring-payment system. LDK does
not need to remember a subscription, wake up later, or keep a database row for
each payer in order to verify the next request. The invoice can issue an
opaque state value, and the next invoice request can hand that value back. If
the token commits to the offer id, payer signing key, recurrence counter,
start, and payee key material, the payee can check continuity from the request
itself.

That boundary matters because recurrence is full of places where an internal
helper could accidentally become an application API. Cancellation, public
payer-side builders, proportional amount policy, and ChannelManager response
behavior all matter, but none of them had to be decided to make the token
honest. The narrow commit only needed to create next state and verify previous
state. Everything else stayed as pressure for later commits instead of being
smuggled into the first implementation.

The paywindow question landed in the same place. A request outside its
paywindow does not need durable recurrence memory to be rejected. The handler
can look at the current time and decide not to issue an invoice. That kept the
state-token code focused on continuity, not scheduling or policy.

The tests made the shape feel less hand-wavy. The happy path showed the
handoff working, but the more useful checks were the mismatches: wrong offer,
wrong payer, wrong counter, wrong start, wrong key material, malformed state,
and overflow. Those cases are where a stateless design has to prove it is not
just passing bytes around. By the end, the branch still did not have a
complete recurring invoice flow, but it had a small piece that could be trusted
before invoice creation started depending on it.
