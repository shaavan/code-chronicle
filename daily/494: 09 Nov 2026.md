# Log 494: Room for Zero

> 09 November 2026

## What I worked on

- Adapted invoice-request recurrence support to the redesigned offer types on
  the [recurrence branch][continued]. Added the counter, start offset, previous
  state, and cancellation fields, including parsing, serialization, payment
  context plumbing, and rejection on refunds. Public payment APIs remain deferred.
- Flattened the request enum and its two similar payloads into
  `recurrence::Request`, with public fields and borrowed `request_recurrence`
  accessors. Represented cancellation as a boolean, keeping the empty TLV
  conversion at the serialization boundary and preserving wire and persisted
  layouts.
- Moved `Recurrence::period_index` into the offer commit. Separated request-local
  validation from offer compatibility checks, reusing the anchor calculation
  and enforcing the offer's period limit without repeating its own invariants.
- Compared the flattened representation with the original, then restored it.
  Renamed construction to `from_tlv_fields`, ordered the methods by their role,
  and corrected builder and accessor documentation.
- Passed compilation checks for the library, test code, no-std, and fuzz
  configuration, along with documentation generation during the flattening work.
  Later naming and documentation edits passed Rust 1.85 formatting and diff
  checks. No tests were executed and no new coverage was added.

## Reflection

The offer types had already been pulled apart; today I brought the request work
across to use them. Importing the old implementation left another enum with two
similar payloads to read through. Flattening that into four fields made the
request easier to inspect, though exposing those fields meant construction could
no longer be the only place that checked them.

The small rules helped decide where validation belonged. Previous state and
cancellation are invalid at counter zero regardless of the offer, so that check
could stay in a private request helper. Whether recurrence is required or allowed,
which period the request selects, and whether it exceeds the limit need the
offer's terms. The period calculation belonged with those terms too: a fixed
anchor requires a start offset and checked addition, while a first-invoice anchor
forbids the offset and uses the counter directly. Moving that calculation back
into the offer commit gave the request code less to repeat.

I also had to decide how much the request validator should distrust an offer
that had already passed construction or parsing. Optional recurrence with a fixed
anchor is rejected there. Repeating that runtime rejection in request validation
felt unnecessary; one debug assertion was enough to record the assumption.

Temporarily putting the original representation back made the comparison useful.
I still preferred the flat fields when I returned to them, but some of their
types needed to retain distinctions that were easy to overlook. A missing start
offset and an explicit zero mean different things: `Some(0)` works for a fixed
anchor, while a first-invoice anchor requires absence. Previous state likewise
needs to preserve present-but-empty bytes. Those options stayed. Cancellation
could become a boolean because its empty TLV only signals presence.

By the end, the remaining edits were small enough to judge while reading: a
constructor name that says it consumes TLV fields, documentation that describes
borrowed accessors, and a plain `if` for the counter-zero rule. I liked leaving
that rule easy to see. Compilation covered the changed shapes across several
configurations, but the request behavior still needs tests.
