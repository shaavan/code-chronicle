# Log 445: Kept in the Flow

> 17 August 2026

## What I worked on

- Continued the recurrence branch from state-token helpers into invoice
  creation.
- Kept the public invoice response API on the existing `respond_*_no_std`
  methods instead of adding recurrence-specific response variants.
- Moved next-state issuance into `flow.rs`, where verified recurring requests
  can attach recurrence state to the invoice builder.
- Tied the emitted invoice recurrence basetime and the next-state token to the
  same `created_at` value.
- Updated the invoice-creation tests to build recurring requests, attach next
  state, and reject missing previous state or counter overflow.

## Reflection

Today was about making the state token useful without letting it take over the
API around it. The previous pass proved that a recurring invoice request could
carry enough information for stateless continuity. This pass had to connect
that proof to the message the payer actually receives next: the invoice.

The first implementation made the pressure visible in the wrong place. Adding
methods like `respond_using_derived_keys_with_recurrence_next_state_no_std`
worked mechanically, but it made the ordinary invoice response path read as if
recurrence had become its main job. That felt off. Most invoice responses
should not need to know about recurrence at the call site, and a recurring
request should still travel through the same basic response machinery as any
other verified request.

Moving the recurrence work back inside the offers flow made the boundary
cleaner. The public builder path stayed familiar. When the verified request is
recurring, `flow.rs` creates the nonce, derives the next-state token, and
attaches it to the `InvoiceBuilder`. That is the place with enough context to
know whether recurrence state belongs on the invoice at all, and it keeps the
policy close to invoice creation instead of leaking it into a new public
response surface.

The basetime detail was small but important. The invoice recurrence fields and
the state token have to point at the same recurrence moment, or the handoff
would be technically present but hard to trust. Using `created_at` for both
kept that relationship concrete. The comments now mark the non-obvious parts:
the common response methods are intentionally unchanged, recurrence state
cannot be attached to a non-recurring builder, and the token commits to the
basetime the invoice actually emits.

The tests helped settle the shape after the API was pulled back. They now
construct recurring invoice requests directly, recompute and sign the tagged
hash, build through `respond_with_no_std`, then add next state through the
builder. The assertions are less about whether bytes appear somewhere and more
about whether the handoff is coherent: basetime matches `created_at`, the next
state verifies for the next counter, and invalid continuity does not quietly
produce an invoice.

By the end, recurrence reached invoice creation without making every invoice
response look recurrence-specific. Cancellation and payer-side public behavior
still remain outside this slice, but the branch now has a real bridge from the
stateless helper to the invoice field that carries the next handoff.
