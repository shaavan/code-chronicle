# Log 477: Room to Retry

> 10 October 2026

## What I worked on

- Corrected both submission paths on the [recurrence branch][recurrence-branch] to record a failed attempt when the channel manager rejects the payment immediately. An attempt becomes active only after successful submission.
- Moved success and failure event updates into atomic store mutations, rechecking the active payment ID inside each mutation. Already-handled events leave the record untouched; missing records and persistence errors still request replay. Corrected cancellation's store update and added an explicit `NotFound` check.
- Added an automatic recurrence retry task using the existing runtime and shutdown mechanism. It scans every thirty seconds, refreshes failed active recurrences, and retries within the payment window using a fresh payment ID. Only success advances the recurrence.
- Corrected the validator used by submission so an initial failed payment without an offer basetime can retry. Removed the duplicate validator and closed-window assertion; the recurrence-limit assertion remains.
- Kept shared submission and window-validation helpers in the manual-payment commit, with the periodic trigger in the later retry commit. Added the missing `InvalidRecurrence` error to the UniFFI declaration.
- Passed formatting, diff checks, all 166 existing library tests, and the UniFFI build check. New retry tests were removed; operation-wide race prevention and recovery from persistence failures after submission remain deferred.

## Reflection

The day started with a store update in cancellation, then returned to the failed send that yesterday's work had left awkward. A recurrence could still look busy after the channel manager rejected its payment. Before a timer could help, that state had to describe what was actually running. Fixing both submission paths gave a rejected attempt somewhere to go, and checking the payment ID inside event-handler mutations kept an old event from overwriting an intervening change.

I started down a manual retry path before working through the design. Backoff and persisted retry times were also considered, but the decision settled on a fixed node-level interval, separate from LDK's ten-second retry budget within an attempt. LDK-Node already had independent background loops, so another task fit its runtime and shutdown handling. The retry keeps the same recurrence and period, with a fresh payment ID each time. A failed attempt should not move the schedule forward.

Reviewing the cherry-picked commit caught the part that the timer alone could not solve. The initial-payment exception sat in a validator submission never called. With no offer basetime and no first successful payment, the old check had no start time to use and would block every retry. Moving the exception onto the actual path let that first payment try again; success then saves the invoice's basetime for later window checks. A closed window also had to return an error without panicking the periodic task. The existing tests and bindings check passed, though the broader races and persistence ordering still need work. The loop now has a usable failed state to return to.
