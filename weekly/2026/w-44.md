# Weekly Log 44: Recovery, Attempts, and Open Questions

> 23 October 2026 – 30 October 2026

## Overview

The inbound recurrence work moved from deciding what to store into testing what
survives a failed write, a restart, or an older event arriving again. Simplifying
the record made it easier to follow, but the first recovery run exposed a fault
in the test adapter itself. The correction compiles; the recovery assertions
still need another run.

On the payer side, the manual lifecycle came together around a saved attempt
and a shared submission gate. Cancellation had to leave enough information for
a later outcome, which changed the order of the implementation stack. The week
ended with Onion Message V2 planning: reading the proposal and reference code,
then reducing a broad checklist to implementation stages and three concrete
spec-review questions.

## Highlights

### Keeping enough inbound history

- Replaced the acceptance map, next-counter field, and latest-success field
  with an ordered `completed_payments: Vec<PaymentId>` and a separate pending
  reservation. Positions supply counters, length supplies the next counter,
  and older confirmations can check the payment ID at their position.
- Removed compatibility code for the unreleased layout and repaired references
  exposed by rearranging the stack. Completed lookup and listing through
  detached public snapshots; UniFFI API exposure remains deferred.
- Reduced six persistence and API tests to four recurrence-specific checks for
  serialization, persistence and snapshots, snapshot replacement, and corrupt
  startup data. All four passed with default features and `uniffi-default`.
- Added nine focused test functions to the [inbound recurrence PR][inbound-pr]
  for restart recovery, reservation ownership, progress, replay, cancellation,
  persistence failures, concurrent reservations, context validation, and
  completion boundaries. Tests exercise the production event handler without
  live channels; recovery rebuilds from saved bytes, and a write barrier forces
  competing reservations to overlap.
- Traced the run's single failure, alongside 173 passes, to the adapter calling
  `InMemoryStore::write` before checking whether to inject a failure. The call
  changed saved bytes even though the adapter reported failure. Deferred it
  until after the barrier and failure check, preserving the assertions.
  Compilation passed, including with UniFFI; the correction remains uncommitted
  and a fresh test run is still needed.

### Keeping an outbound attempt through its outcome

- Made payer-side storage naming explicit while preserving TLV layouts. Lookup
  and listing return cloned `OutboundRecurrenceDetails`, without a separate
  snapshot type. Added offer-aware amount and quantity validation, checked
  multiplication, and persistence of the relationship and initial attempt
  before submission.
- Routed initiation, manual next payments, and retries through one gate that
  rechecks lifecycle status, attempt ownership, the pending payment record, and
  timing under the mutation lock. The lock stays held through synchronous
  queueing. Retries use a fresh payment ID without advancing paid progress.
- Moved combined success and failure handling ahead of cancellation in the
  stack. Addressed inclusive completion limits, repeated events, late success,
  and partial-write recovery. Payment success is persisted before recurrence
  progress; a later failure preserves the successful payment record.
- Serialized cancellation with submission and retained the abandoned attempt's
  payment ID. A late success can record progress while leaving the relationship
  cancelled. Local cancellation remains effective if queueing its remote
  request fails, with the error returned to the caller.
- Drafted the [outbound recurrence PR][outbound-pr] around the manual Rust APIs.
  Formatting, diff checks, and library builds passed with and without UniFFI.
  Focused lifecycle tests remain deferred, along with restart reconciliation,
  automatic scheduling, binding exposure, and handling another success when
  the `u32` paid count is already at its maximum.

### Finding the questions in Onion Message V2

- Mapped BOLT PR #1367 onto rust-lightning and LDK Node in an
  [implementation tracker][omv2-tracker]. Reviewed the fixed header, eight
  routing slots, separate encrypted payload, Python reference implementation,
  and vector generator. Most implementation belongs in rust-lightning;
  Node needs downstream adoption and mailbox compatibility work.
- Organized milestones from packet primitives and transport through routing,
  applications, and release validation. Kept relay support separate from
  complete BOLT12 invoice-request and invoice-reply flows.
- Narrowed spec-review questions to a visible prefix meeting a blinded tail,
  forwarding when the next peer is disconnected, and locally peeled dummy
  hops. Compact-path size, application audits, and retries remain implementation
  work. Authenticated context and BOLT12 path integration still need design.

## Reflections

I liked how little the completed-payment vector needed to explain. The pending
reservation already holds the accepted payment, and an ordered list can remember
the successful ones without keeping the same progress in several fields. That
made the record smaller while retaining what replay needs. It also made the
remaining reservation problem harder to overlook: a claim that never produces
`PaymentClaimed` still needs evidence that it cannot succeed before its counter
can be released.

The recovery test gave that concern a more immediate form. I expected a failed
write followed by a restart to expose the state the node would actually recover.
Instead, the adapter had already changed the bytes before reporting failure.
Following the failure into that call was useful; weakening the assertions would
have left the test describing an interrupted write it never created. The fix
is small, but the next run still has to establish that recovery holds with the
intended saved state.

Returning to outbound recurrence brought a related ordering problem into the
submission path. Saving an attempt did not guarantee that it still owned the
right to be queued. Cancellation or another reservation could intervene. Keeping
the checks and queueing under the same lock gave those callers a definite order.
I also had to move outcome handling earlier in the stack before cancellation
could be finished. Once an attempt might already be in flight, its ID has work
left to do even after the caller has cancelled the relationship.

OMv2 changed the pace at the end of the week. The first tracker contained many
things I needed to investigate, and fewer things that needed an answer from
the specification. Tracing specific cases helped separate them. A visible
prefix can unknowingly create a bounce inside a blinded tail. Node's mailbox
can defer OMv1 forwarding, while OMv2 explicitly says to ignore a message whose
next peer is disconnected. Peeling dummy hops locally still has to satisfy the
rule against consecutive identical nodes. Those are concrete questions to take
back to the proposal; the application audits can proceed as implementation work.

The recurrence APIs now have enough shape to test their interleavings directly.
The immediate work is to rerun inbound recovery and give outbound submission,
cancellation, and late outcomes the same scrutiny. OMv2 has an implementation
order too, with packet forwarding as an early milestone and the full BOLT12
exchange still ahead.
