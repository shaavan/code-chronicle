# Log 475: What Falls Away

> 08 October 2026

## What I worked on

- Reviewed the [blinded-path fee fix][blinded-path-fees] and its existing offers test, which changes the expected fee from 1050 to 50 msat when the payer skips its own introduction hop.
- Added a focused regression test with nonzero base fees, proportional fees, and CLTV deltas. Advancing past the payer reduces aggregate fees from 201 msat and 1001 ppm to 100 msat and 500 ppm, and the CLTV delta from 300 to 156 blocks, while preserving HTLC bounds and removing the correct hop.
- Removed an unrelated decryption assertion and distinguished preserving downstream dummy-hop fees from directly testing fee removal for a skipped dummy hop.
- Refined the proposed commit message and PR description to explain the general path-advancement behavior. Formatting and whitespace checks passed; tests stayed unrun under the repository instructions. The regression test remains uncommitted, with no production changes made.

## Reflection

I started by looking for one test that would add something to the fix. The offers test already showed the payment-level result: the payer’s skipped introduction fee disappeared, and the downstream dummy-hop fee remained. The original problem was easy to see there. A recipient could put the payer at the introduction hop, attach large fees, and receive extra money from the routing-fee budget even though the payer never forwarded through that hop. I wanted the new test to make the arithmetic underneath that result visible.

Giving both forwarding hops nonzero fees made the remainder worth checking. Their aggregate includes rounding, so advancing the path has to recover the remaining hop’s exact fees. I initially also checked whether the forwarder could decrypt its instructions afterward. Removing that assertion felt right once I saw that it was checking existing blinding-point behavior. The fee regression gave the test enough to do.

Returning to the report also made me more careful with the description. The reported exploit concerned a payer-owned introduction hop; the method updates the aggregate whenever it successfully removes a forwarding or dummy hop. It leaves HTLC bounds conservative and the path unchanged on error. The existing offers test does not directly exercise every part of that behavior, especially skipping a dummy hop itself. Keeping those limits explicit helped me describe the fix without asking either test to prove more than it checks. The new test still needs a run.
