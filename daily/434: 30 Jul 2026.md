# Log 434: Exact Enough

> 30 July 2026

## What I worked on

- [Continued] the currency branch by answering two reviewer threads around
  `CurrencyConversion` and payer-side amount verification.
- Kept the `ChannelManager` docs conservative about when
  `NullCurrencyConversion` is enough and when a real converter is needed.
- Folded the converter documentation into the commit that introduces the new
  parameter, instead of leaving it as a separate cleanup.
- Updated `verify_amount_acceptable_for_payment` so explicit invoice-request
  amounts must match the returned invoice amount exactly.
- Added a regression test for a currency-denominated offer where a requested
  `10_000` msat invoice is answered with `10_001` msat and rejected with
  `InvalidAmount`.

## Reflection

The currency branch picked up two review comments that looked close together
at first, because both touched the question of what the payer should know
about converted amounts. They ended up pulling on different parts of the
payment flow. One was about documentation and type plumbing. The other was a
real verification hole.

The `CurrencyConversion` docs needed to stay more cautious than the obvious
answer. It would have been nice to say that offer-only nodes can keep using
`NullCurrencyConversion` if they always resolve amounts themselves, but
`pay_for_offer_intern` does not work that way. Currency-denominated offers
still call `to_msats_range(&self.currency_conversion)` before the explicit
`amount_msats` path gets to settle the payment amount. That means a null
converter can fail before the caller's concrete amount helps.

So the documentation now says the thing the code can actually promise: nodes
that may create or pay `Amount::Currency` offers need a converter, while nodes
that do not use currency conversion can keep the null implementation. Folding
that wording into the plumbing commit also made the history read better. The
parameter and the warning about its limits now arrive together.

The second thread was sharper. The existing payer-side check rejected explicit
amounts below the locally converted minimum, but review pushed on whether the
payer should enforce that rule at all when the caller deliberately supplied
`amount_msats`. The payee can reject an amount it will not accept. The payer's
job in that case is narrower: if it asks for one amount, it should not silently
pay a larger invoice.

That exposed the bug. For currency offers with an explicit invoice-request
amount, parse-time validation uses `NullCurrencyConversion`, so equality
validation can be skipped when conversion fails. Payment-time verification
covered the no-explicit-amount currency path, but it did not force an explicit
request amount to match the returned invoice. A payee could answer a `10_000`
msat request with `10_001` msat, and the payer would route using the invoice's
larger amount.

The fix made the two cases separate. Explicit invoice-request amounts are now
checked directly and must match exactly. The omitted-amount currency path still
uses the configured converter to enforce the maximum payable amount. That
keeps the payer from over-constraining a caller-provided amount while still
protecting the caller from paying more than it asked for.

The regression test was useful because it sits on the part of the flow that
parse-time validation could miss. A currency offer asks for `10_000` msat, the
invoice comes back at `10_001`, and payment verification returns
`InvalidAmount`. The branch feels better for having the rule stated in that
plain form. When the caller is explicit, exactness is the contract.
