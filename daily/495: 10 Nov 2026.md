# Log 495: The First Timestamp

> 10 November 2026

## What I worked on

- Adapted invoice recurrence support on the [recurrence branch][continued]. Added
  basetime and optional next-state fields, threaded basetime through invoice
  creation, and rejected recurrence on refunds and static invoices while
  preserving the imported wire layout.
- Moved invoice recurrence data into `recurrence.rs` with public `basetime` and
  `next_state` fields. Renamed the request and invoice types to `RequestFields`
  and `InvoiceFields`, applying each rename at its place in the commit stack.
- Centralized basetime resolution in `RequestFields::resolve_basetime`, replacing
  a macro shared across request wrappers. Renamed the value recovered from
  previous state to `recovered_basetime` and removed a verification placeholder
  that always returned `Ok(None)`.
- Aligned parsing with invoice creation: recurrence presence must match the
  request, fixed anchors must match the offer's basetime, and the first invoice
  for a first-invoice anchor must use its creation time. Clarified accessor
  documentation for optional recurring offers receiving non-recurring requests.
- Passed formatting, diff checks, documentation generation, and compilation,
  including test code and no-std. No tests were executed and no new coverage was
  added. Drafted the invoice-support commit message; edits remained uncommitted
  for incorporation into the stack.

## Reflection

Bringing the invoice changes across made the schedule's starting point more
concrete. The request selects a counter, but the invoice has to carry the basetime
that gives that counter a place on the schedule. A fixed anchor already supplies
it. A first-invoice anchor needs the initial invoice's creation time, then needs
that same value back on later requests. Those cases were easier to follow once
the calculation lived in one request-fields method and the wrappers only handled
the context they actually owned.

The previous-state verification placeholder was awkward to leave in place. It
always returned `Ok(None)`, so calling it gave the code the appearance of a step
that did no work. Removing it meant the verified-request constructors initialized
`recovered_basetime` to `None` directly. The plumbing for recovery stayed, and
later requests with a first-invoice anchor still fail without a recovered value.
That leaves a visible gap to fill when state authentication arrives. I preferred
being able to see it at construction.

Parsing needed to hold the same rules as creation. An invoice cannot introduce
recurrence that its request did not use, omit recurrence that it did use, or
choose another basetime for a fixed anchor. Counter zero with a first-invoice
anchor ties the basetime to creation time; later counters have to retain the
original schedule. Writing those checks also exposed a small documentation trap:
an offer can permit recurrence without every request using it. The accessors
needed to describe the request being answered.

The remaining cleanup was mostly careful reading. `RequestFields` and
`InvoiceFields` say what the structs contain without suggesting they are whole
messages. `recovered_basetime` says where that particular value comes from.
Restoring unrelated signatures and indentation kept those changes easier to
judge in the stack. The code compiled across the checked configurations, but
state recovery is still deferred and the invoice behavior still needs tests.
