# Log 437: Next Tick

> 03 August 2026

## What I worked on

- [Continued] the async static-invoice refresh branch through another review
  pass around pending refresh state, close batching, and test setup behavior.
- Fixed a hidden dependency in the channel-update test by draining the setup
  refresh before configuring the static invoice server.
- Changed forced refresh plumbing so failed refresh enqueueing re-marks the
  pending flag instead of silently losing the later retry.
- Removed leftover splice scaffolding and the now-unneeded
  `force_refresh_async_receive_static_invoices` helper.
- Changed channel-close handling back to the batched pending-refresh path so
  batched force closes do not send intermediate static-invoice updates.

## Reflection

The static-invoice refresh branch came back to the same surface, but the shape
of the work was different this time. Earlier passes had been about deciding
which channel changes make cached server-side invoices stale. Today was more
about the smaller places where the branch could still be depending on timing,
helper behavior, or a too-eager refresh.

The test failure was a good example. The channel-update test looked like it was
starting from a quiet baseline, but initial channel setup had already delivered
`ChannelUpdate`s and set the async refresh flag. The test only avoided seeing
that because an earlier helper tick happened to consume the pending refresh.
Draining the setup refresh before configuring the static invoice server made
the test less magical. The assertion now starts from state it deliberately set
up instead of from state another helper happened to leave behind.

The forced refresh path had a more serious version of that problem. It cleared
the pending bit before knowing whether all selected `ServeStaticInvoice`
updates were actually enqueued. If building an invoice or reply path failed,
the cache could still be stale while the retry signal had already been erased.
Making the flow report whether every selected update was enqueued gave
`ChannelManager` the missing feedback. A failed forced refresh now marks the
pending bit again, so the next timer tick still has a reason to rebuild.

Some of the day was just removing shape that no longer explained itself. Once
close refreshes were routed through `check_refresh_async_receive_offer_cache`,
the dedicated force-refresh helper stopped earning its name. The splice scope
was similar. Review was right that it looked suspicious, but the answer was
not to turn splices back into a refresh trigger. It was old scaffolding from an
earlier version of the branch, and removing it made the intended splice
non-behavior clearer than another comment would have.

The close path changed because the immediate answer had its own problem.
Refreshing inside `finish_close_channel` matched the finalization boundary, but
batched force closes made that less clean in practice. A loop of closes could
send several server updates and build invoices from channel state that was
still in the middle of settling. Marking the same pending refresh flag used by
forwarding updates gave closes the same batching behavior. It gives up the
instant refresh, but it avoids teaching the server about every intermediate
state in the close batch.

By the end, the branch felt less like it was trying to be clever about when to
act. Setup work is drained explicitly. Failed forced refreshes leave a retry
behind. Splices do nothing because this branch does not need them to do
anything. Channel closes mark the cache stale and let the timer rebuild once
the surrounding churn has settled. The pending bit is doing more of the work
again, and this time that feels like the steadier place for it.
