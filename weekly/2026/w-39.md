# Weekly Log 39: Giving the Stack Edges

> 28 September 2026 – 29 September 2026

## Overview

The recurrence work moved from proving pieces of the payment lifecycle to
working out how the full stack should be reviewed. The `PaymentSent` path now
looks up recurrence state by active payment ID and records success through the
store, while integration coverage captured validation failures and persisted
failed submissions. The handler remains incomplete, with missing types and
fields elsewhere still blocking a full compile.

That unfinished implementation made the review boundary more important. The
stack was divided into four proposed PRs, from durable foundation through
bindings and documentation. Checking the actual branches exposed a checkout
that still pointed at the full stack and an unrelated formatting commit in the
lifecycle branch ancestry. The split now has concrete edges to align against,
though the recovery and management PR still looks large.

## Highlights

### Keeping recurrence payment state small

- Kept recurrence state to active and last-successful payment IDs, leaving
  `PaymentDetails` in `PaymentStore`.
- Added `PaymentSent` lookup by active ID, then cleared that ID and saved the
  successful payment ID through the store.
- Covered validation failures and persisted failed submissions; replaced an
  invalid hand-built offer with a deterministic no-route case.
- Targeted integration and serialization roundtrip tests passed. The broader
  handler remains blocked by incomplete manager and model pieces.

### Finding reviewable stack boundaries

- Split the stack into four sequential PRs: durable foundation, core payment
  lifecycle, recovery and management, then events, bindings, and documentation.
- Confirmed the Foundation checkout still held the full stack; a later branch
  contained the six intended dependency, state, serialization, and storage
  commits.
- Defined eight lifecycle commits in `node-recurrence-B`; its ancestry still
  includes an unrelated rustfmt cleanup commit to resolve during alignment.
- Drafted the overall description around the BOLT 12 proposal and the division
  between rust-lightning protocol work and LDK Node lifecycle and management.

## Reflections

The payment path now has a small, understandable piece of state to follow. A
recurrence remembers the payment in flight and the last one that succeeded;
the store already owns the details. That kept the success and failure cases
from growing a second copy of payment data. The targeted tests could verify
those transitions, even while the rest of the handler still lacks pieces it
needs to compile.

Reviewing the stack required a different kind of tracing. The first Foundation
checkout looked plausible until I checked its commits and saw the full stack
still there. The lifecycle branch was closer to its intended boundary, though
one formatting commit had slipped into its ancestry. Those details matter
because a useful PR should leave behind a piece reviewers can understand on
its own.

Four stages give the work a sequence, but recovery and management still carry
more than feels comfortable. The description now says where the protocol work
ends and the node lifecycle begins. Next comes aligning the real branches to
that split, then seeing whether the third PR can be made easier to review
without breaking its recovery story apart.
