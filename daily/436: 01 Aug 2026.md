# Log 436: Verified Once

> 01 August 2026

## What I worked on

- [Continued] the currency branch by moving invoice-request amount resolution
  into `verify_invoice_request`.
- Reworked the `respond_with_*` invoice paths so builders receive a verified
  millisatoshi amount instead of resolving currency themselves.
- Reused `Bolt12SemanticError` for invoice-request verification instead of
  adding a separate error type.
- Kept the excessive-amount errors needed by invoice-side payment verification
  while leaving the old insufficient-amount case out of the flow.
- Removed currency-conversion validation from `OfferBuilder` and updated the
  changelog around where conversion failures can happen.

## Reflection

Yesterday left the currency branch with the right instinct but an awkward
shape. The payable amount needed to be computed during invoice-request
verification, then carried forward as the value invoice construction could
trust. The first pass still had too many places where currency could be
interpreted, which made the builder API look like part of the validation
story.

The reviewer suggestion made the boundary sharper. `verify_invoice_request`
should read the request, apply the currency rules, and produce the concrete
millisatoshi amount. After that, the invoice builder should not need a
converter at all. It should receive the amount it is allowed to put in the
invoice. That removed the uneasy feeling that the request and a separately
threaded amount could drift apart.

The API cleanup followed from that. The `respond_with_*` paths no longer need
to accept a converter just to reconstruct the same answer later. The separate
`respond_with_amount` helper also stopped earning its place once the public
`respond_with` path could carry the verified amount directly. It made the
surface smaller in a way that matched the design: verification decides, invoice
construction records.

The error work had the same pressure. Introducing a new
`VerifyInvoiceRequestError` made this path feel more detached from the rest of
BOLT12 semantic validation than it actually is. Returning to
`Bolt12SemanticError` kept the failure model closer to the existing offer and
invoice-request checks. The excessive-amount cases still matter on the
invoice-payment side, so those stayed. The insufficient-amount case no longer
had a useful role once request verification owned the payable amount.

The second review thread pulled offer construction out of validation too. A
converter in `OfferBuilder` would only prove that this node can convert an
advertised currency at construction time. That is the wrong place to ask the
question. An offer can record a currency-denominated amount, but the creator is
responsible for advertising currencies it can price when invoice requests
arrive. The docs now say that directly instead of making the builder pretend it
can enforce the future.

The changelog needed the same wording discipline. It no longer describes
offer builders as rejecting unsupported currencies. Conversion failures belong
to invoice-request and invoice verification, where there is an actual amount
to resolve and an actual payment decision to make. That left the branch feeling
less tangled: offers describe, verification resolves, and builders consume the
verified result.
