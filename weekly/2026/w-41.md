# Weekly Log 41: Before Leaving It Running

> 07 October 2026 – 12 October 2026

## Overview

The failed recurrence state from the previous week gained a way back into
submission. Manual payments first exposed a missing payment-ID association
and a send failure that could leave a recurrence looking busy. Correcting
those transitions made retry possible, then a periodic task raised the next
questions: when to pay another period, when to mark it missed, and what to do
while an earlier payment still has no outcome.

Alongside that work, I reviewed two blinded-path fixes. One followed an extra
message-content field through dummy-hop processing; the other checked which
fees and CLTV delta should remain after skipping a hop. Both needed careful
explanations of what the regression coverage actually proves. By the end of
the stretch, a public recurrence retry operation was committed separately,
while the broader scheduler remained uncommitted and still needed tests.

## Highlights

### Checking what a blinded hop accepts and retains

- Reviewed the [dummy-hop rejection fix][dummy-hop-fix]. An unknown odd outer
  TLV is skipped by the parser but still sets `message_type`, exposing a
  rejection difference between forwarding and dummy hops.
- Traced how a sender can add that field around unchanged authenticated
  routing instructions. The privacy explanation now keeps the observable-reply
  requirement explicit; silence alone does not establish where dummy hops begin.
- Moved the regression test and supporting imports into a test-only module.
  Formatting, whitespace, and the Rust 1.75 default-library build check passed;
  follow-up corrections remained uncommitted and the test stayed unrun.
- Added focused coverage for the [blinded-path fee fix][blinded-path-fees],
  checking exact remaining base and proportional fees and CLTV delta after
  advancing past the payer, while preserving HTLC bounds. Removed an unrelated
  decryption assertion and kept downstream dummy-fee preservation distinct
  from directly testing a skipped dummy hop. The new test remained uncommitted
  and unrun.

### Giving retry a usable submission path

- Refined manual-payment eligibility and saved the submitted payment ID in
  recurrence state so later success and failure events can find the attempt.
  Checked the inclusive recurrence limit and identified an early completion
  boundary that was corrected in the later scheduler work.
- Corrected both submission paths to record immediate rejection as a failed
  attempt. Success and failure handlers now recheck the active payment ID
  inside atomic store mutations; already-handled events leave state untouched,
  while missing records and persistence errors request replay.
- Added a thirty-second retry task using the existing runtime and shutdown
  handling. Retry keeps the same period and uses a fresh payment ID; only
  success advances the recurrence.
- Moved the initial-payment exception onto the validator submission actually
  calls, allowing retry without an offer basetime. Shared helpers stayed with
  manual payment, and the periodic trigger stayed in its later commit.
- Passed all 166 existing library tests and the UniFFI build check at that
  stage. New retry tests were removed, leaving the new behavior without its
  own regression coverage.

### Working out automatic progression

- Separated and committed a public operation for retrying one recurrence on
  the [recurrence branch][recurrence-branch], then built the broader scheduler
  separately. It scans at startup and every thirty seconds, handles failed,
  missed, and completed recurrences, and pays future periods when a persisted
  setting enables it.
- Shared completion and window checks across scheduling, manual payment, and
  event handling. Automatic payments target period start, or window opening
  for early-only windows; failed attempts can retry throughout their window.
  Pending payments wait for an outcome even after the window closes.
- Persisted an attempt reservation before queueing and rechecked cancellation
  before submission. An ongoing submission finishes recording its result
  during shutdown, but a crash between reservation and submission can still
  strand the reservation.
- Passed formatting, whitespace, and default and UniFFI library compilation
  checks for the scheduler. Tests stayed unrun and these changes remained
  uncommitted.

## Reflections

The recurrence work kept taking me further into the submission path than I
expected. Saving a payment record did not give the event handler enough to
find its recurrence. Saving an active ID did not help when submission failed
immediately and left that ID looking busy. Once those cases were corrected,
the failed state had something useful to do: permit another attempt within
the same window, without advancing the period.

The timer made progress visible, but it also made the remaining decisions
harder to leave implicit. Overlapping windows could pull successive payments
ahead of their periods. A closed window could still contain a pending payment
whose result had not arrived. I liked separating the retry operation before
broadening the scheduler; it gave that work a smaller submission path to reuse
while the timing rules were worked through.

Persistence ordering was the part I was least comfortable leaving alone. A
successful submission followed by a failed state write could make the next
scan retry a payment already running. Reserving first closes that route, but
a crash before submission can leave the recurrence waiting on an attempt
that never started. That case remains open.

The blinded-path reviews also kept me close to the evidence. A reply matters
to the dummy-hop probe, and preserving a downstream dummy fee does not prove
fee removal when that dummy hop is skipped. The same care mattered when
describing recurrence: checks on an intermediate implementation could not
support guarantees absent from the committed code. The existing suite passed
before the broader scheduler changes. Next comes testing those timing and
reservation paths, including what can recover a stranded attempt, before
leaving recurrence to progress on its own.
