# Log 459: The First Durable Intent

> 08 September 2026

## What I worked on

- Aligned LDK Node with the recurrence-enabled rust-lightning and compatible
  `bitcoin-payment-instructions` revisions, including the supporting
  onion-message resolver correction.
- Added incoming recurring-offer cancellation translation with offer and payer
  identity preserved through serialization and replay.
- Reworked outbound amount handling so `PaymentSent::amount_msat` is used when
  available without losing amounts from older or incomplete events.
- Introduced durable recurrence state and a dedicated persistence namespace,
  keeping the payment index as a rebuildable cache rather than the authority.
- Implemented initial recurrence registration and submission, persisting
  `Prepared` state before the LDK call and testing the resulting acceptance
  boundary.

## Reflection

The first implementation pass started with dependency alignment rather than
recurrence behavior. Updating only LDK Node was not enough: the newer
`bitcoin-payment-instructions` revision already depended on a specific
recurrence-enabled rust-lightning commit. Following that chain led through a
small onion-message resolver correction and back into Node with a compatible
set of revisions. The cancellation event then had to carry its offer ID and
payer signing key all the way through persistence and replay.

The next problem was quieter but just as important. Successful outbound
payments could arrive with an amount in `PaymentSent`, while older or
incomplete events left the local record as the only source. Making the event
amount authoritative when present, without discarding the stored fallback,
removed the old panic and kept variable-amount BOLT 12 payments consistent.

That work made the shape of recurrence state harder to avoid. The record now
holds the identity, offer, payment policy, schedule position, basetime,
optional state, attempt, retry and automation settings, cancellation state,
and lifecycle transition. It lives in its own durable namespace. The payment
index can speed up lookups, but restart and cache misses must return to the
stored recurrence records.

Initial submission established the boundary that will govern the rest of the
feature. Node validates the offer, creates its recurrence and payment IDs,
persists `Prepared` state, and only then asks LDK to submit the invoice
request. A synchronous failure is recorded against that durable intent rather
than erasing it. The operation can return an error before intent exists; after
that point, the state has to explain what happened. That gave the later
payment and recovery work a place to begin.
