# Weekly Log 34: Where State Belongs

> 24 August 2026 – 26 August 2026

## Overview

This week kept asking which pieces of state should cross an API boundary and
which ones should stay behind it.

The recurrence branch started with payer signing key derivation. The recurring
relationship needs a stable identity that LDK Node can persist, but the key
material that signs invoice requests belongs inside LDK. Adding
`RecurrenceId` gave Node a durable handle, while deriving the payer key from
`RecurrenceId`, `OfferId`, and `ExpandedKey` kept private material out of the
message builder. The builder ended up with the narrow input it actually needs:
a payer pubkey for metadata derivation, followed by an unsigned invoice
request that the outer flow can sign.

That boundary shaped the public recurrence API next. `PaymentId` stayed tied
to one payment attempt, and `RecurrenceId` stayed tied to the recurring
relationship. `pay_for_recurrence` could then look like the offer-payment path
where it should, without pretending recurrence is only another single payment.
Cancellation made the split more concrete. It still uses invoice-request
encoding because that is where recurrence proof lives, but it does not ask for
an invoice, does not carry amount or retry state, and does not create pending
outbound payment state.

The week ended by moving back to dummy-hop fee reporting. Deferred onion decode
made exact recipient-side dummy fee accounting restart-sensitive. Keeping
`dummy_skimmed_fees_msat` would have meant adding persistent accumulator state
for a temporary decode path. Dropping the field left the branch centered on
dummy-hop behavior, sender fee expectations, relay constraints, fee bucketing,
and exposed path construction instead of exact event accounting that did not
survive the new boundary cleanly.

## Highlights

### Keeping recurrence keys inside LDK

- Added `RecurrenceId` as the stable identifier LDK Node can create and
  persist for a recurring relationship.

- Derived recurrence payer signing keys from `RecurrenceId`, `OfferId`, and
  `ExpandedKey`, so private signing material stays inside LDK.

- Reworked invoice-request construction to accept a payer pubkey for metadata
  derivation and return an unsigned invoice request.

- Removed `Keypair` and then `RecurrenceId` from the builder after both put
  too much flow-local state into generic message construction.

- Covered derivation invariants and verified that recurrence payer metadata can
  be signed with the matching derived key.

### Giving recurrence APIs their own shape

- Kept `PaymentId` and `RecurrenceId` separate so payment attempts and durable
  recurrence relationships keep different lifetimes.

- Moved recurrence-specific payment inputs into their own params struct while
  leaving `amount_msats` as the invoice-request amount.

- Split cancellation into `RecurrenceCancellationParams` and
  `cancel_recurrence`, with no amount, retry config, or pending outbound
  payment state.

- Removed the reply path from cancellation requests and fixed receiver-side
  handling so verified cancellations can be classified before responder
  checks.

- Added payer and event coverage for no-reply-path cancellation, stable payer
  key derivation, missing outbound state, and invalid `counter == 0`.
  ([Branch][recurrence])

### Letting dummy-hop accounting stay smaller

- Revisited dummy-hop fee reporting after deferred onion decode made exact
  recipient-side accounting depend on state that may not survive restart.

- Dropped the separate `dummy_skimmed_fees_msat` recipient event field instead
  of adding persistent accumulator state around temporary decode machinery.

- Removed event-field plumbing, deferred dummy-fee accumulator state, and test
  helper reads that depended on exact dummy-hop fee exposure.

- Rebuilt the remaining dummy-hop stack around underflow logging, fee
  bucketing, realistic dummy relay constraints, and exposed path construction.

- Fixed sender fee expectations to include sender-paid dummy-hop fees while
  keeping recipient claimable amount checks tied to the amount actually
  received. ([Branch][dummy])

## Reflections

The recurrence work this week was mostly about resisting convenient places to
store things. A `Keypair` in the builder would have made the first API easy to
wire, but it also would have made message construction responsible for signing
material it should never own. `RecurrenceId` in the builder was less severe,
but it still put node-level relationship state inside a generic BOLT 12
message path. Passing only the payer pubkey left the builder with enough
identity to derive metadata and no more.

That same separation made the public API easier to read. A recurring payment
still creates an invoice request and eventually a payment attempt, so
`PaymentId` remains part of the flow. But the relationship that survives
between attempts is a different thing. Letting `RecurrenceId` feed key
derivation makes that lifetime visible without asking callers to manage the
key itself.

Cancellation was the place where the API stopped being able to hide behind the
normal payment path. It uses the same proof machinery as a recurring invoice
request, but everything after that is different. There is no invoice to wait
for and no outbound payment to track. Removing the reply path forced the
receiver to verify before deciding whether a missing responder was an error,
which matched the shape of the message better than preserving the old
ordering.

The dummy-hop branch had a similar pressure in a different part of the code.
Exact dummy-fee reporting was attractive because it preserved a precise number
on recipient events. The problem was the state needed to justify that number
after deferred decode and restart. Adding accumulator persistence would have
made a temporary path heavier just to keep one field alive.

Dropping the field made the remaining stack more honest. The sender still pays
the dummy-hop fees, so sender fee expectations include them. The recipient
still reasons about what actually arrived. The tests now describe those two
surfaces separately instead of trying to carry exact dummy-hop accounting
through an event boundary that no longer naturally has the data.

By the end of the week, both branches had the same kind of answer: durable
relationship state belongs where it can be owned, signing material stays
inside the layer that can protect it, and exact accounting only crosses a
boundary when the code can keep proving it there.
