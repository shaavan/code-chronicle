# Log 484: Enough to Remember

> 23 October 2026

## What I worked on

- Simplified success history on the [inbound recurrence branch][recurrence-branch]
  to `completed_payments: Vec<PaymentId>`, keeping the pending reservation
  separate. Each index supplies its counter, the length gives the next counter,
  and replay checks the payment ID stored at that position.
- Removed compatibility code for the unreleased record layout and repaired
  constructor and event-handler references left behind when the stack moved.
  Identified comment-only cherry-pick changes for folding into the reservation
  commit.
- Completed lookup and listing through `Node::inbound_recurrence` and
  `Node::list_inbound_recurrences`, returning detached snapshots. Default and
  UniFFI-feature compilation passed; binding exposure remains deferred.
- Checked the implementation against the plan, separating outdated
  cancellation-only records from follow-up work on missed windows and failure
  handling. A reserved payment that never produces `PaymentClaimed` still needs
  a safe way to release its counter.
- Reduced six persistence and API tests to four focused checks covering record
  serialization, persistence and public snapshots, snapshot replacement, and
  corrupt recurrence data at startup. All four passed with default features
  and `uniffi-default`; the final test reductions remain uncommitted.

## Reflection

The acceptance history from the previous session gave replay enough information,
but I kept coming back to how much of it repeated the rest of the record. A
pending reservation already says which payment has been accepted. Once that
payment succeeds, its place in the completed list can carry the counter. Keeping
those two things separate let me remove the acceptance map, next-counter field,
and latest-success field without losing the older payment IDs replay needs. I
liked how little explanation the vector needed once its ordering was doing that
work. The compatibility code was less useful: this layout is still in
development, so I removed it rather than reconstruct an earlier representation.
Rearranging the commits then exposed a few stale field references that needed
fixing before the branch compiled again.

Checking the plan took some care because it still described decisions we had
already dropped. Cancellation-only records were one of those. The failure case
was still real, though. Ordinary payment failures already have handling in the
node; the recurrence problem starts when a payment owns a reservation and has
been submitted for claiming, then never produces `PaymentClaimed`. Releasing
that counter needs evidence that the whole payment can no longer succeed. The
unused `Failed(PaymentId)` state can wait for that work. Giving it a transition
without that evidence would leave the reservation rule unfinished in a less
obvious way.

The tests needed a similar pass through what was already there. I started with
six and then compared their assertions with existing coverage. Generic lookup,
pagination, decoding errors, and update results did not all need another test
here. I kept the recurrence-specific checks, including separation between
offer-and-payer pairs and replacement of public snapshots, and dropped repeated
assertions. Four tests passed in both feature configurations. That gives the
stored record and public API some validation, while the claim, cancellation,
and replay transitions still need their own tests.
