# Log 503: Without a Token

> 23 November 2026

## What I worked on

- Reviewed the [recurrence stack][continued] one concern at a time. Confirmed
  that compulsory-recurrence rejection and the automatic response builders'
  `c_bindings` conversion were already covered, and identified commit messages
  that no longer described the code accurately.
- Made cancellation amount access return `None` safely when no amount exists.
  Prevented direct responders from issuing payable invoices for cancellations
  and rejected received invoices answering cancellation requests, using semantic
  errors for both cases.
- Removed blanket previous-state requirements from request validation and token
  creation. Fixed-anchor follow-ups can use the offer's basetime; first-invoice
  follow-ups still require a recoverable original basetime. Supplied tokens
  remain authenticated, and cancellation can omit state.
- Documented caller-owned timing policy for direct responders and configurable
  enforcement in the automatic flow. Limited recurrence validation during
  verification to requests containing recurrence fields. Investigated payment-ID
  reservation ordering, then removed the local fix so both payment APIs can be
  corrected together upstream.
- Folded paywindow work and review fixes into their owning commits, resolving
  overlaps without changing the final code. The fourteen-commit stack ended with
  a clean worktree. Formatting, diff checks, Rust 1.75 and C bindings compilation,
  and relevant rustdoc checks passed. Tests were not run.

## Reflection

The previous-state checks looked reasonable while I pictured every invoice being
created by the automatic flow. Each follow-up would return the token from the
last invoice, and the recipient would recover what it needed. That became awkward
once I considered an application creating an invoice manually, then handing later
requests back to automatic handling. Leaving `next_state` out of that invoice
would prevent the handoff even when the offer already supplied the schedule's
basetime.

I initially considered documenting that restriction. Working through the manual
case made it hard to justify keeping it everywhere. A fixed-anchor offer already
carries its basetime. A first-invoice anchor needs the original invoice's creation
time for later requests, so those still fail when it cannot be recovered. An
initial request can establish that time when its invoice is created. Cancellation
does not need an invoice basetime at all. Those cases gave the validation enough
information to decide without requiring a token from every follow-up. A supplied
token still has to authenticate, and neither its presence nor its absence proves
that an earlier period was paid.

Cancellation needed another pass through the public APIs. Construction and
parsing already allowed omitted amounts, but the accessor could still panic on
that valid request. Direct responders could also try to turn a cancellation into
a payable invoice. Returning semantic errors there matters because applications
can call those APIs directly, just as received messages can carry unexpected
inputs. I kept those checks separate from paywindow enforcement. Reusing the full
automatic validator in direct responders would take away the caller's choice to
accept an early or late request, undoing the policy separation from the previous
recurrence session.

The payment-ID ordering issue took a different route. I implemented reservation
before enqueueing, cleanup on enqueue failure, and delayed retry activation, then
confirmed that the ordinary single-payment API had the same problem. I removed
the unstaged fix rather than leaving the recurrence stack to solve only half of
it. The final autosquash needed care too: later commits could restore the state
requirements I had just removed. Checking the final tree against the code before
autosquash kept that review grounded. The stack now permits the manual-to-automatic
handoff where the schedule supports it; the shared payment-ID correction and
behavioral tests remain open.
