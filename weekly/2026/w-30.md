# Weekly Log 30: One Place to Decide

> 28 July 2026 – 03 August 2026

## Overview

This week moved across three review threads, but most of the pressure gathered
around one question: where should a value become trusted enough for the rest of
the flow to use it?

The dummy-hop branch needed its proof to move up to the router. Earlier work
had made dummy `PaymentConstraints` depend on downstream context, but the test
still lived too close to helper construction. The better check decrypts the
router-built forward, dummy, and receive payloads, then walks the visible
constraint chain directly. That keeps the privacy claim tied to the route a
sender actually builds.

Most of the week then stayed with currency-denominated offers. Review pushed
the branch away from treating conversion as general plumbing and toward
deciding amounts at the one point where the request can be read with enough
context. Explicit `amount_msats` should not be rejected against the payer's
local FX minimum before the payee answers, but the returned invoice still has
to match the requested amount exactly. Invoice-request verification now owns
that resolution, and invoice builders receive a concrete millisatoshi amount
instead of carrying conversion logic themselves.

The static-invoice refresh branch closed the week by tightening pending
refresh behavior. Setup refreshes are drained deliberately in tests, failed
forced refreshes re-mark the pending bit, and channel closes now take the
batched path so force-close loops do not send intermediate server updates.

## Highlights

### Proving dummy constraints through the router

- Replaced local dummy-hop constraint comparison with router-level coverage
  that exercises `Router::create_blinded_payment_paths`.

- Kept dummy relay policy selection separate from derived dummy constraints,
  with the dummy tail built outward from receive-side constraints.

- Decrypted forward, dummy, and receive payloads in the test and checked that
  the downstream-plus-delta chain stays continuous across the dummy boundary.

- Verified that the old placeholder constraints are gone from router-built
  dummy payloads instead of only from helper-built sequences. ([Branch][dummy])

### Keeping currency conversion out of static invoices

- Removed currency-conversion plumbing from async static-invoice offer
  creation, receive handling, and `ChannelManager::initiate_async_payment`.

- Left ordinary BOLT12 invoice currency conversion intact while making
  static-invoice receive-side amount handling local and bitcoin-only.

- Split the current cleanup from the follow-up rule that amountful static
  invoices should be rejected directly.

- Removed stale tests and docs that still described currency-denominated async
  static-invoice payments as supported. ([Branch][currency])

### Making explicit amounts exact

- Updated payer-side verification so an invoice returned for an explicit
  invoice-request amount must match that amount exactly.

- Added regression coverage where a `10_000` msat currency request answered
  with a `10_001` msat invoice fails with `InvalidAmount`.

- Stopped rejecting explicit currency amounts against the payer's locally
  converted minimum before the recipient has answered.

- Kept maximum-value checks on the final explicit or inferred amount,
  including inferred bitcoin totals after quantity multiplication.

### Resolving invoice requests once

- Moved invoice-request amount resolution into `verify_invoice_request`, so
  verification computes the payable millisatoshi amount and carries it forward.

- Reworked `respond_with_*` invoice paths so builders receive the verified
  amount instead of resolving currency themselves.

- Reused `Bolt12SemanticError` for invoice-request verification failures,
  keeping this path with the rest of BOLT12 semantic validation.

- Removed currency-conversion validation from `OfferBuilder` and updated
  changelog language around where conversion failures can happen.

### Letting static-invoice refreshes batch

- Drained setup refresh state in the channel-update test before configuring the
  static invoice server, so assertions no longer depended on helper timing.

- Changed forced refresh plumbing so failed enqueueing re-marks the pending
  refresh flag and leaves the next timer tick with work to do.

- Removed leftover splice scaffolding and the now-unneeded force-refresh
  helper.

- Routed channel-close refreshes back through the batched pending-refresh path,
  avoiding intermediate server updates during batched force closes.
  ([Branch][static])

## Reflections

The currency work gave the week its center because the same amount can mean
different things at different points in the protocol. Before an invoice
request is sent, an explicit `amount_msats` is the payer saying what it is
willing to ask for. It is not proof that the payee will accept that amount at
the payee's exchange rate. Rejecting it against the payer's local converted
minimum made the payer stricter than the protocol shape required.

After the invoice comes back, the rule changes. If the payer asked for
`10_000` msat, a `10_001` msat invoice is no longer a conversion disagreement
to tolerate. It is a different payment than the one requested. Separating
those two moments made the branch easier to hold: request creation should stay
less presumptive, and invoice verification should be exact about what the
caller agreed to pay.

Moving payable amount resolution into `verify_invoice_request` was the part
that made the rest of the cleanup feel less like plumbing. The builder API had
been pulled into validation because it could still receive a converter and
interpret currency while constructing the invoice. Once verification reads the
request and produces the amount, construction has a smaller job. It records a
verified value. That also made `OfferBuilder` simpler. An offer can describe a
currency-denominated amount, but proving that the creator can price that
currency belongs to the later request-handling path.

The dummy-hop test work had a similar concern with where proof belongs. A
helper-level comparison could show that two artificial constructions matched,
but the branch needed to show that sender route construction itself no longer
leaves dummy constraints with invented-looking sentinels. Decrypting the
router-built payloads made the test follow the same pressure as the privacy
claim. The dummy layer still marks itself as dummy, but its visible constraint
chain now comes from the same downstream context as the hops around it.

The static-invoice refresh work closed the week by making pending state carry
failure and batching more honestly. Clearing a pending bit before every update
has been enqueued can lose a retry. Refreshing during each close in a force
close batch can publish server-side invoices from a channel set that is still
in motion. Marking stale state and letting the timer rebuild once the churn has
settled is less immediate, but it fits the cache's job better.

By the end of the week, the useful pattern was concrete enough to trust:
values should be interpreted where the needed context is present, then passed
forward in the form later code can actually use. Dummy constraints come from
the route. Currency amounts come from invoice-request verification. Static
invoice refreshes come from pending state that survives failure and batches
channel churn. Each branch got smaller once that boundary stopped moving.
