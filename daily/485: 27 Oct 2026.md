# Log 485: What the Failure Wrote

> 27 October 2026

## What I worked on

- Added nine focused test functions to the [inbound recurrence PR][inbound-recurrence-pr],
  covering restart recovery, reservation ownership, confirmed progress, replay,
  cancellation, persistence failures, concurrent reservations, context validation,
  and completion boundaries.
- Grouped the tests into three commits following the feature commits they
  exercise. Moved context-validation coverage into the claim-handling group,
  where the conversion was introduced.
- Exercised the production event handler without live channels or chain
  services. Recovery tests rebuild from saved bytes; a controlled write barrier
  forces competing reservations to overlap.
- Ran the tests: 173 passed and one failed. Traced the recovery failure to the
  test adapter calling `InMemoryStore::write` before checking for an injected
  failure, which changed stored bytes despite reporting the write as failed.
- Deferred the underlying write until after the barrier and failure check,
  preserving the assertions and removing unrelated formatting changes.
  Formatting, diff checks, and compilation passed, including with UniFFI.
  The correction remains uncommitted, and the tests still need a fresh run.

## Reflection

The previous pass left the stored record and public API with focused coverage.
The transitions needed the same attention, and my first proposal included too
much. Working through what each test could actually catch helped narrow it.
Reservation ownership, an older success arriving again, cancellation on either
side of acceptance, and a restart after a failed write each put pressure on a
different part of the implementation. Separating context validation from the
completion boundaries brought the set to nine test functions. Grouping them
by feature commit also caught an assumption I had made about context conversion:
it arrived with claim handling, so its test belonged there.

The recovery test was the part that resisted. It rebuilt the node from saved
bytes before retrying, which should have made a failed persistence step visible.
The run ended with 173 passing tests and one failure. Following that failure
led into the adapter itself. `InMemoryStore::write` changes its bytes when called;
waiting on the returned future is already too late to stop that change. The
adapter had created the future before deciding whether to inject a failure.
The test was reporting a failed write while giving the restarted node the
bytes that write was supposed to have left untouched.

Moving the call after the failure check repaired that setup. I kept the
assertions and cut the unrelated formatter changes from the correction. It was
useful to find this in a test that reads the saved state again: the adapter's
reported result alone would have hidden what had happened. Compilation passed,
but I still need to rerun the tests before treating the recovery case as settled.

The event tests can stay in a separate file under `src/event/`; their scaffolding
would make `event.rs` harder to read. The context-conversion test would fit
better beside `payment/inbound_recurrence.rs`, since it does not need event
handling. That move remains undone. For now, the coverage is in place and the
adapter correction is small enough to review with the commit that introduced
it. The next run needs to show whether the recovery assertions hold with a
failure that actually leaves the saved bytes alone.
