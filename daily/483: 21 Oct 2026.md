# Log 483: What Cancellation Leaves

> 21 October 2026

## What I worked on

- Added cancellation on the [inbound recurrence branch][recurrence-branch],
  using the same mutation lock as acceptance. Cancellation blocks new claims
  while preserving an already accepted reservation; later success records
  progress without clearing `Cancelled`.
- Restored required recurrence terms after reconsidering cancellation without
  an existing record. A missing record now returns `ReplayEvent`; preventing
  future invoice issuance remains work for LDK request handling.
- Narrowed recurrence rejection to safely failing an existing matching inbound
  payment record. Restored the shared failure helper and unrelated callers,
  preserving accepted, successful, outbound, and unrelated records without
  creating records for newly rejected payments.
- Added durable payment-ID-to-counter acceptance history alongside reservations.
  Older confirmations can finish remaining payment-record and event writes
  without advancing twice or disturbing newer reservations. Existing successful
  payment records can help recover history predating this tracking.
- Ran formatting, diff checks, and library compilation checks. Tests were
  neither added nor run, and feature changes remain uncommitted for review.
  Startup reconciliation and reservation release after confirmed failure remain
  deferred; user notifications retain at-least-once delivery.

## Reflection

Yesterday's reservation gave an accepted payment somewhere to wait. Cancellation
made me work through what could still happen while it waited. If cancellation
arrives first, a new claim should stop there. If acceptance gets the lock first,
that payment already owns its counter. Its eventual success still needs to be
recorded, even though the relationship stays cancelled. Sharing the mutation
lock gave those two cases a definite order. I briefly made recurrence terms
optional to allow cancellation without a stored relationship, then backed that
out. The current handling needs an existing record; stopping future invoices
still belongs in request handling.

Repeated events needed more memory than the latest successful payment ID could
provide. Once newer payments have progressed, an older confirmation still needs
to be recognized. Saving payment IDs with their counters gives replay something
durable to check before touching progress or a newer reservation. That also
helped me keep the recovery work bounded. An event delivered again can finish
writes left incomplete. Unfinished work with no event to replay needs startup
reconciliation, which is still ahead.

The rejection path took a smaller correction. I had changed the shared failure
helper too broadly, and tracing its effects brought the change back to the
recurrence case. A rejected payment should not damage an accepted one or leave
a new failed record just because it was refused. I also spent time making the
comments say what the code does and why the remaining work is deferred. There
are still no tests behind these transitions. Compilation passed, but the cases
where cancellation, replay, and partial writes meet need more validation before
I can be comfortable with them.
