# Log 432: Route-Shaped Proof

> 28 July 2026

## What I worked on

- [Continued] the dummy-hop follow-up branch by replacing the local
  constraint comparison with router-level coverage.
- Narrowed the reviewer concern around dummy-hop `PaymentConstraints` to the
  visible downstream-plus-delta chain, instead of trying to make dummy TLVs
  structurally identical to forward TLVs.
- Reworked router construction so dummy relay policies stay separate from
  derived dummy constraints, with the dummy tail built from the receive
  constraints outward.
- Fixed a small ownership issue where extracting `forwarding_info` partially
  moved `details` before the router code was finished with it.
- Added a `blinded_payment_tests` case that decrypts router-built forward,
  dummy, and receive payloads and checks that placeholder constraints are not
  retained.

## Reflection

The dummy-hop constraint work needed one more pass because the code fix and
the proof of the fix were not quite at the same level. Yesterday's version had
made complete dummy TLVs depend on downstream constraints, which was the right
invariant. But the test still lived too close to the helper shape. It could
show that two manually constructed sequences agreed with each other, while
leaving the router path less directly exercised.

Review made the boundary of the claim sharper. Dummy payloads still have their
own marker, so the branch is not trying to pretend a decrypted dummy TLV is an
ordinary forward TLV in every field. The important part is narrower and more
practical: a padded blinded path should not expose a different
`PaymentConstraints` chain from the one ordinary forwarding would have built
from the same downstream constraint and relay CLTV deltas.

That pushed the implementation back toward the route itself. Relay selection
can stay random in production and deterministic in tests, but complete dummy
constraints need to be derived only when the downstream hop is known. Building
the dummy tail outward from the receive constraints, reversing it into path
order, and feeding the upstream-most dummy constraints into the first real
forward hop made the accounting continuous across the dummy boundary.

There was a small Rust reminder in the middle: `forwarding_info` could not be
pulled out of `details` while the rest of `details` was still needed. Cloning
that small value before turning it into `PaymentRelay` was not interesting by
itself, but it kept the router flow readable. The code could say what it was
doing without an ownership workaround becoming the story.

The better test now follows the same path a sender actually uses. It builds
real blinded payment paths through `Router::create_blinded_payment_paths`,
decrypts the forward, dummy, and receive payloads, and checks the constraint
chain at each step. It also verifies that the old `{ u32::MAX, 0 }`
constraints are gone. That matters because the failure mode was always a
little too quiet: a value that passed validation could still reveal that it
was invented outside ordinary forwarding.

By the end, the branch felt less like it had a patched invariant and more like
the invariant had a place to stand. The dummy layer still exists as a dummy
layer, but its constraints now move through the same route-shaped pressure as
the hops around it. That is the part the test needed to prove.
