# Log 439: Structural Holds

> 06 August 2026

## What I worked on

- [Continued] the currency branch through another pass on static-invoice
  amount handling and BOLT12 parsing behavior.
- Added claim-path coverage for unverifiable currency invoice requests so the
  payee side fails closed when the expected amount cannot be derived.
- Replaced a reachable static-invoice payer `debug_assert` path with a
  defensive `UnverifiableAmount` abandon and covered the currency-offer case.
- Fixed currency tolerance math so sub-msat per-unit tolerance survives until
  the final invoice amount is applied.
- Tightened parser and builder invariants around explicit invoice-request
  amounts and zero currency-denominated offers.

## Reflection

The currency stack needed a different kind of review today. Earlier passes had
mostly been about finding the right owner for conversion. This pass was more
about the places where that answer was already known, but the surrounding code
still carried older assumptions from bitcoin-denominated offers.

The claim side had one of the quieter holes. The existing underpayment tests
proved that a derived amount could be compared, but they did not cover the
case where the expected currency amount could not be derived at all. That is a
smaller-looking branch, but it is the one that decides whether uncertainty
gets treated as acceptable. Adding the test made the behavior explicit:
without a verifiable amount, the invoice request does not get claimed.

The static-invoice payer path had the same pressure in a louder form. It still
had an old `debug_assert!(false)` for a state that became reachable once
currency offers entered the flow. A static invoice has no invoice amount of
its own, and a currency offer without an explicit invoice-request msat amount
cannot be priced by that payer path. Leaving that as an assertion would make
the code depend on a model the branch had already changed. Returning
`UnverifiableAmount` and abandoning the payment is less dramatic, but it is the
honest answer for that state.

The tolerance bug put pressure on the rounding boundary. Computing
basis-points tolerance per minor unit meant tiny rates lost their tolerance
before the invoice amount had a chance to scale it back into a real
millisatoshi value. Preserving the fractional adjustment first made the math
match the economic intent instead of the intermediate representation.

The parser work landed on a similar distinction. An explicit invoice-request
msat amount is already in the unit the invoice uses. It should not be routed
through `NullCurrencyConversion` just because the underlying offer is
currency-denominated. Checking `invoice_request.amount_msats()` first closed
that gap and gave the regression test a concrete failure mode: a requested
`1000` msat invoice mutated to `2000` now rejects as `InvalidAmount`.

The zero-amount builder fix was the other side of that boundary. Builder code
still should not pretend to validate exchange rates, but a nonzero amount is a
structural invariant, not a market question. The parser already rejected the
zero currency TLV, so allowing the builder to sign it made the local API more
permissive than the wire format it was meant to produce.

By the end, the rule felt steadier: conversion-aware checks stay where a
converter exists, while structural facts are enforced before conversion enters
the picture. That kept the branch from using uncertainty as an excuse to skip
basic validation, and it kept the builder from growing into a pricing oracle.
