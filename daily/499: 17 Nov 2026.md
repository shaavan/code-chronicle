# Log 499: One Payment at a Time

> 17 November 2026

## What I worked on

- Completed payer-side basetime enforcement on the [recurrence branch][continued].
  Returned invoices must match the expectation saved with their request, after
  invoice authentication and payment ID matching.
- Added `recurrence::Id` to derive a stable payer signing key from the recurrence
  ID, offer ID, and expanded key. Payments and cancellations share that identity;
  individual requests retain fresh metadata and their own payment IDs. Internal
  builders reject signing keys that do not match.
- Added `ChannelManager::pay_for_recurrence` and `RecurrencePaymentParams` for
  requesting one payment at a time. Persisted `expected_basetime` in retryable
  request state through a new optional TLV, preserving existing tags and the
  validation context across retries and restarts.
- Added `cancel_recurrence` and `RecurrenceCancellationParams`. Cancellation
  requires a nonzero counter, the original starting period, and unchanged previous
  state when present. It queues a notification without a reply path or pending
  payment. Updated construction and parsing to allow omitted amount and quantity
  while continuing to validate supplied values.
- Refined API documentation and commit boundaries. Formatting, diff checks, MSRV
  compilation including test targets, no-default-features compilation, and
  documentation builds passed. No tests were executed and no new coverage was
  added.

## Reflection

The saved basetime expectation from yesterday now has an enforcement point. Once
an invoice has been authenticated and matched to its payment ID, the payer checks
it against the rule recorded when the request left. A non-recurring request must
stay non-recurring. The first request with a first-invoice anchor uses the
invoice's creation time; fixed anchors and follow-ups require an exact value.
Recording those cases first made this part easier to follow. An accepted invoice
can no longer quietly move the payer onto another schedule.

The payment API needed a payer identity that could last across requests. Each
request needs its own payment ID and fresh metadata, but the recipient needs to
recognize the same payer across a recurrence, including its cancellation. `recurrence::Id`
gives key derivation that stable input without making individual requests share
all their identity. The caller still has work to do: retain the recurrence state,
choose when to request the next payment, and supply the established basetime for
later requests with a first-invoice anchor. Each API call asks for one payment.
Carrying `expected_basetime` into retryable state keeps that call's original
expectation intact when the request outlives the process that sent it.

Cancellation exposed a gap in the shared request validation. The recipient path
already knew that a cancellation produces no invoice, yet construction and
parsing still required the amount and quantity needed for a payment. Checking
the draft led to allowing either field to be absent for cancellation, with
supplied values still checked. Separating the two branches in
`check_amount_and_quantity` made the difference easier to read. The API's success
also needed a modest meaning: the notification was queued locally. There is no
reply path promising delivery or acknowledgement.

The last pass was mostly about leaving the stack readable. Moving the shared
builder's final cancellation parameter into the preceding payment commit avoided
changing its signature again immediately, while the cancellation behavior stayed
together. Review also found that requests are queued before duplicate-payment
detection in both this API and the ordinary offer path. That needs a shared
correction and remains open. I liked reaching a usable payer API, though the
compilation checks still leave its behavior, retries, and cancellation handling
without new test coverage.
