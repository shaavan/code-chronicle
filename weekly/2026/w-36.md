# Weekly Log 36: A Boundary That Can Recover

> 08 September 2026 – 14 September 2026

## Overview

This week recurrence crossed from design into a durable LDK Node foundation,
then became large enough to require its own review map. The first source pass
aligned Node with the recurrence-enabled rust-lightning revisions, introduced
durable records, and established the acceptance boundary: persist `Prepared`
intent before asking LDK to submit a payment. Later work carried that boundary
through successful payments, failures, retries, cancellation, restart
recovery, lifecycle events, and the Rust and UniFFI APIs.

The implementation made several ownership lines concrete. The recurrence
record is authoritative; the payment index is a rebuildable cache. Paid
progress advances only after a correlated, validated payment. Manual and
automatic payment share policy without sharing an implicit claim. Cancellation
is terminal locally, while remote continuity exists only after a successful
payment. These rules survived serialization, replay, and binding work, though
some recovery and scheduling edges remain open.

The final days turned from implementation to history and review. Removing
out-of-scope amount behavior, using rust-lightning's `RecurrenceId` directly,
and placing fixups beside the commits that caused them made the 33-commit
stack compile and tell a more accurate story. Reducing the current 31-commit
PR to storage, lifecycle, recovery, and application-facing responsibilities
gave the next review a sequence instead of one large pile.

## Highlights

### Establishing durable recurrence

- Aligned LDK Node, `bitcoin-payment-instructions`, rust-lightning, and the
  onion-message resolver correction at compatible revisions.

- Added incoming cancellation translation with offer and payer identity
  preserved through serialization and replay.

- Introduced durable recurrence records in a dedicated namespace, leaving the
  payment index as a rebuildable lookup cache.

- Persisted `Prepared` state before initial submission, recording synchronous
  failure against durable intent once that boundary had been crossed.

- Used `PaymentSent::amount_msat` when present while retaining stored amounts
  for older or incomplete events.

### Making payment state advance safely

- Correlated successful payments with their attempts and validated invoices
  before advancing paid recurrence state.

- Preserved basetime, optional state, payment IDs, completion, and replay
  behavior across first and later payments.

- Kept expiry, rejection, route failure, abandonment, and unknown outcomes
  from damaging paid progress or retry windows.

- Added manual later-period payments with checked counters, fresh payment IDs,
  window boundaries, amount and routing policy, and no skipped periods.

- Rebuilt the payment index during recovery and reconciled prepared attempts
  with LDK's recent-payment list before scheduler startup.

### Exposing lifecycle control

- Added opt-in automation, persisted retry policy, exponential delays, caps,
  closing-window precedence, and protection against duplicate attempts.

- Added mutable routing overrides, including explicit clearing back to
  node-wide configuration, without changing manual payment behavior.

- Made cancellation abandon active attempts, preserve remote continuity data
  when available, and become locally terminal through `CancellationPending`.

- Exposed inspection, listing, payment, cancellation, removal, configuration,
  routing, and lifecycle-event APIs in Rust and UniFFI.

- Added replay coverage for stable transition IDs, validated hexadecimal
  identifiers, default and `uniffi-default` builds, focused tests, and
  formatting checks.

### Keeping implementation and history honest

- Removed outbound amount changes that broadened ordinary payment behavior
  beyond recurrence requirements.

- Replaced the local `RecurrenceId` wrapper with rust-lightning's upstream
  type while retaining Node-specific storage and hexadecimal handling.

- Moved serialization and import corrections to the commits whose changes
  required them, compiling the stack with Cargo 1.98.

- Reduced the 31-commit PR to storage, lifecycle, recovery, and application
  concerns, then grouped it into four possible sub-PRs.

- Recorded remaining serialization, incoming-cancellation translation,
  recovery resubmission, scheduling, atomic claiming, and configuration-order
  coverage gaps for the next review chunks.

## Reflections

The first durable intent changed how the rest of the implementation had to be
read. Before submission, an operation can still return an ordinary error.
After Node records its intent, failure becomes part of recurrence state and
has to survive a restart. That single ordering decision pulled persistence,
event handling, recovery, and scheduling into the same conversation.

Payment success then supplied the fact that the protocol itself cannot infer
from invoice issuance. A payee can issue an invoice without being paid, so
the next counter must come from durable `PaymentClaimed` progress. The record
advances only after attempt correlation and invoice validation. Failures clear
the active attempt but leave paid progress and basetime untouched. Replays
must apply the same transition once, not move the schedule again.

Automation and cancellation showed that durable state is also where races
become visible. Recovery must finish before automation scans records. Retry
cannot cross an exclusive closing boundary. Cancellation can abandon local
work and remain terminal even if a late success arrives. A remote cancellation
only has continuity data after a payment has established a relationship. The
rules are compact, but each one depends on which side of the boundary owns
the fact.

The binding pass was a useful test of that ownership. Fixed-byte IDs and LDK
types should not become accidental UniFFI contracts. Validated hexadecimal
wrappers made the public surface stable, while the documentation had to say
what durable acceptance, amount ceilings, routing overrides, and removal
actually mean after restart. The replay test added a similar constraint for
events: duplicate delivery repeats one transition; a later transition remains
distinct.

By the end of the week, code and history needed the same treatment. The
amount fallback was broader than recurrence required, and a local ID wrapper
was no longer justified once the upstream type was available. The compiler
and commit history both exposed those seams. Reviewing the reduced PR then
made the remaining uncertainty more manageable: four possible sub-PRs, each
with concrete questions around crash points, duplicate events, concurrent
callers, and restart behavior. [The reduced recurrence stack][recurrence-review]
now gives that work a sequence. The foundation is in place; the next work is
proving its edges rather than adding more surface.
