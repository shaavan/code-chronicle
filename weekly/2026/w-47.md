# Weekly Log 47: One Request Later

> 12 November 2026 – 17 November 2026

## Overview

The recurrence work started with a missing basetime and ended with APIs for
requesting individual payments and sending cancellation notifications. Between
those points, the schedule had to survive being issued in an invoice, echoed in
a later request, carried into a payment path, and checked by the payer when an
invoice came back. Each step gave the timestamp somewhere concrete to go.

Cancellation followed the same payer identity and authenticated state, while
shedding requirements that only make sense when an invoice is coming back.
The stack now has both sides of that exchange, with retryable state preserving
the payer's original expectation. Compilation and documentation checks passed;
behavioral coverage and a shared request-queueing issue remain ahead.

## Highlights

### Recovering the schedule and checking the window

- Added state-token verification on the [recurrence branch][recurrence-branch]
  to recover the period-zero basetime. Tokens bind the encrypted basetime, offer
  ID, payer signing key, expected next counter, optional start offset, and nonce.
  They permit replay and do not prove that the preceding invoice was paid.
- Added automatic next-state issuance to both invoice signing paths, using fresh
  entropy and the invoice's captured creation timestamp. Follow-up requests need
  previous state in this flow, and counter overflow prevents token creation.
  Manual responses can still omit tokens; builders reject state attached to
  invoices answering non-recurring requests.
- Carried recurrence terms and basetime together through authenticated blinded
  payment paths. Moved persistence support for the flattened recurrence types
  into the earlier offer commit, preserving absent defaults and offer wire
  encoding, with persisted requirement discriminants `0` for optional and `1`
  for compulsory.
- Centralized automatic response validation on `VerifiedInvoiceRequest<S>`.
  Both invoice creation paths recheck the payment window before allocating
  payment data, using the same timestamp that creates the invoice and issues
  its token. A request waiting after verification can otherwise outlive its
  valid window.

### Giving cancellation its own path

- Routed verified cancellations to `RecurringOfferCancelled`, carrying the
  offer ID and payer signing key. They require authenticated previous state,
  produce no invoice, and need neither a reply path nor a payment-window check.
  Shared the state requirement across validation, token creation, and handling.
- Made cancellation events persist across restart. Retained even event tag
  `54` so unsupported readers reject the pending event rather than silently
  drop it. Replayed requests can produce duplicate notifications; applications
  still need idempotent handling.
- Added `cancel_recurrence` and `RecurrenceCancellationParams`. The API requires
  a nonzero counter, the original starting period, and unchanged previous state
  when present. It queues a notification without creating a pending payment;
  local queueing promises neither delivery nor acknowledgement.
- Updated request construction and parsing to permit omitted amount and quantity
  for cancellation, while retaining validation of supplied values. The recipient
  path already avoided invoice creation, but the shared request checks had still
  required payment fields.

### Remembering what the payer requested

- Added `BasetimeExpectation` to reply-path context, then enforced it after
  invoice authentication and payment ID matching. Non-recurring requests must
  remain non-recurring; fixed anchors and follow-ups require an exact basetime;
  the first request with a first-invoice anchor expects invoice creation time.
  Older contexts default to `NonRecurring`.
- Added `recurrence::Id` for stable payer signing-key derivation from the
  recurrence ID, offer ID, and expanded key. Payments and cancellation share
  that identity, while individual requests keep fresh metadata and separate
  payment IDs. Internal builders reject mismatched signing keys.
- Added `ChannelManager::pay_for_recurrence` and `RecurrencePaymentParams`.
  Each call requests one payment. Persisted `expected_basetime` in retryable
  request state through an optional TLV, preserving existing tags and the
  original acceptance rule across retries and restarts. Callers retain recurrence
  state and decide when to request the next payment.
- Refined documentation and commit boundaries as the imports came together.
  Formatting, diff checks, documentation builds, and compilation passed across
  the applicable test targets, MSRV, no-std, and fuzz checks. No tests were
  executed and no new coverage was added. Review also found that requests are
  queued before duplicate-payment detection in both the new API and the ordinary
  offer path; that shared correction remains open.

## Reflections

Last week's invoice work could name the basetime without recovering it for a
later request. The token gave that missing value a way back. I liked being able
to follow the same schedule through the exchange, but reading the authentication
code also made its limits specific. A valid token ties a request to the expected
offer, payer, and counter. It cannot tell the recipient whether an earlier invoice
was paid, and it does not stop the same request from arriving again. Those facts
belong beside the mechanism because applications will have to work with them.

Time introduced another gap even after the state was authenticated. Verification
can happen while a window is open, with invoice creation delayed until it has
closed. The captured creation timestamp was already keeping the invoice and its
token in agreement; using it for the final window check put the decision where
the response is actually made. Carrying the terms and basetime together into the
payment path extended that same care to the context returned with payment.

Cancellation kept exposing assumptions borrowed from payment. First it needed
somewhere to go without producing an invoice. Later, the payer API showed that
construction and parsing still demanded amount and quantity. Working through
both ends helped remove those requirements without weakening checks on values
that are supplied. The event can survive a restart, but replay can still deliver
it twice. Queueing the outgoing notification also remains a smaller promise than
knowing the recipient received it.

Reaching the payer API felt good. A recurrence can keep one signing identity
without making its requests share payment IDs or metadata, and a retry can retain
the basetime it was originally prepared to accept. The caller still owns the
schedule and asks for one payment at a time. That gives the next tests concrete
behavior to exercise: echoed state, a request waiting across a window boundary,
invoice acceptance after retry, and cancellation replay. The duplicate-payment
ordering needs a shared fix too. The build checks have carried the stack this
far; those paths still need to run.
