# Weekly Log 42: What Comes Through

> 14 October 2026 – 15 October 2026

## Overview

The recurrence work returned to planning after the outbound scheduler work.
Reading the nine-commit stack helped separate what already existed from what
the inbound path still needed. Following a payment from claim acceptance to
confirmed receipt exposed an LDK metadata prerequisite and gave the proposed
stores, reservations, and PR boundaries more concrete jobs.

The other thread was a blinded-path padding fix. Rounding each forwarding
payload independently could leave different encrypted lengths visible to the
payer. The change now measures the non-final payloads together and gives them
one shared size. A regression covers the rounding boundary and a dummy hop,
though its first run stopped at compilation and a successful rerun remains
unverified.

## Highlights

### Planning around the inbound events

- Reorganized `plan.md` into inbound recurrence, outbound recurrence, and shared
  work, marking implemented steps and placing remaining fixes beside the
  behavior they affect. No recurrence code changed during this pass.
- Planned an inbound store keyed by offer ID and payer signing key, keeping
  separate relationships when a payer key is reused across offers. Records
  retain terms, timing, paid progress, and cancellations that arrive before
  the first payment.
- Identified missing recurrence terms and invoice basetime in
  `Bolt12OfferContext`. Adding them in LDK would let Node recover the metadata
  through authenticated blinded payment paths without needing the full invoice
  in the event.
- Assigned cancellation and sequential-counter checks to claim acceptance,
  with pending reservations held until confirmed receipt advances progress.
  Existing atomic store mutations can serialize cancellation with acceptance
  or submission. Claiming must also allow valid payments whose request window
  has since closed.
- Kept stranded-claim cleanup open: `claim_funds` returns no result to roll back
  against, and clearing a reservation needs evidence that the payment cannot
  succeed later. Outbound API gaps, quantity-scaled amounts, initial-attempt
  reservation, and cancelled payment associations remain planned work. Shared
  reconciliation, scheduling, bindings, and broader recovery tests follow both
  directions.

### Giving forwarding payloads one size

- Confirmed that independently rounding 24- and 31-byte instructions to
  multiples of thirty produces different padded sizes. Debug builds assert
  equal lengths, but release builds could still expose the difference.
- Updated the [blinded payment padding fix][padding-fix] to choose the largest
  measured padded size across real intermediate and dummy hops. Final-hop
  padding and the helper's large-padding limitation stayed outside the change.
- Added a regression asserting that the two forwarding payloads and a dummy
  payload each encrypt to 76 bytes. Kept the explicit boundary checks after
  considering an alternative test.
- Traced the compilation failure to the iterator's existing clone requirement
  and settled on deriving `Clone` for `BlindedPathWithPadding`. Formatting and
  diff checks passed; a passing test run is still unverified. Prepared the
  commit message and PR description with the #5237 connection and Project
  Loupe credit.

## Reflections

The inbound plan became easier to follow when I traced what the events
actually carry. The full invoice is unavailable there,
and the offer context still lacks terms and basetime. That puts a specific
LDK change ahead of the Node implementation. Separating acceptance from
receipt then kept the state changes honest: accepting a claim reserves its
place, while confirmation advances paid progress.

I had hoped the pending reservations might be removable. Following the gap
between those events made them harder to discard. Another payment can arrive
before confirmation, and there is no claim result to use for an immediate
rollback. Cancellation and late success need their associations too; a late
success can advance a missed recurrence, but it must not undo cancellation.
The plan now retains those cases without pretending stranded reservations
have a recovery rule yet.

The padding work was more contained. Twenty-four and thirty-one bytes were
enough to show why independent rounding could not satisfy the equal-length
expectation. Measuring first gave the fix a small, direct shape, and including
a dummy hop kept the regression close to the privacy concern. I also wanted
the explanation to stop where the evidence stops: distinguishable lengths
can offer clues, but identifying a hidden node requires more information.

This stretch left a recurrence implementation order I could follow and a
padding change whose intended behavior was concrete. The immediate next step
for padding is a passing regression run. For recurrence, the metadata and
stores come first; recovery and scheduling still depend on getting acceptance,
confirmation, and cancellation right in both directions.
