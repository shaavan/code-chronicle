# Log 441: Three Tracks

> 11 August 2026

## What I worked on

- Turned the BOLT 12 recurrence work from a broad protocol read into a more
  concrete issue structure.
- Separated rust-lightning work into wire fields, parsing, validation, period
  helpers, invoice request builder support, and handler logic.
- Drew the boundary between protocol validation in rust-lightning and durable
  recurrence behavior in LDK Node.
- Kept the naming aligned with the current draft terms:
  `invoice_recurrence_next_state` and `invreq_recurrence_prev_state`.
- Split the remaining work across rust-lightning, LDK Node, and spec interop
  instead of treating recurrence as one large feature item.

## Reflection

Today made the recurrence work smaller without making it thinner. The branch
already had several pieces of the protocol surface in motion, and that made
the planning pass more useful than another field-by-field reread. The question
was where each piece should live once the feature stops being a draft in my
head and becomes work that other people need to review.

The rust-lightning side has a clear first layer. It owns the wire shape:
recurrence TLVs, subtype structs, parsing, serialization, and the mirroring
needed for offer fields to move into invoice requests and invoices. It also
owns the validation that depends on those messages. Offer recurrence shape,
request counters, fixed-base start offsets, cancellation markers, and invoice
recurrence fields all need to be checked close to the protocol, because that
is where invalid messages should stop being acceptable.

Period calculation felt like the place where the design could easily become
too convenient. A repeated duration is not enough for this. Month boundaries,
leap behavior, fixed base times, payment windows, and first-invoice starts all
affect what the next valid period means. That logic belongs in rust-lightning
too, because invoice handling should not depend on every caller inventing its
own calendar interpretation.

The LDK Node boundary became sharper once that was written down. rust-lightning
can verify protocol-facing amounts, proportional pricing rules, invoice
issuance, invoice verification, and the state handoff between
`invoice_recurrence_next_state` and `invreq_recurrence_prev_state`. It should
not become the place that stores a user's recurring payments, wakes up on a
schedule, survives restarts, exposes pay and re-pay APIs, or owns cancellation
as wallet behavior. Those are higher-level responsibilities, and putting them
in Node keeps the protocol layer from pretending to be an application.

The naming pass was small, but it helped. Carrying "recurrence token" forward
would have made the issue list slightly out of step with the draft and with
the branch already being cleaned up. The current names describe the direction
of the state: the payee returns next state, the payer stores it, and the next
invoice request echoes it back as previous state. Once that wording was fixed,
the rest of the split became easier to check against the spec.

By the end, recurrence felt less like one large object that had to land all at
once. It had three homes: rust-lightning for the protocol surface and checks,
LDK Node for durable outbound behavior, and the spec work for interop coverage
and merge readiness. That is a quieter kind of progress, but it matters here.
The fields still have to parse, but the harder part is making sure each layer
owns the part of the rhythm it can actually keep honest.
