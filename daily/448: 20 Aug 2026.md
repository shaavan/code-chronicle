# Log 448: The Expected Base

> 20 August 2026

## What I worked on

- Continued the recurrence branch from handler-side cancellation into
  payer-side invoice verification.
- Added explicit reply-path recurrence basetime expectations to
  `MessageContext`.
- Moved expectation construction into the invoice-request path so recurrence
  shape, explicit offer basetime, and follow-up state all stay visible.
- Kept payer-side invoice verification narrow by checking only the invoice
  recurrence basetime on top of existing metadata and `PaymentId` checks.
- Split the stack back into focused context, construction, verification, and
  test commits after verification logic had drifted into the wrong layer.
- Covered the recurrence verifier directly for absent recurrence,
  `invoice_created_at` basetime, matching known basetime, and mismatched
  basetime.

## Reflection

Today was about making the payer know what kind of recurrence invoice it was
allowed to accept. The reply path already carried enough information to get an
invoice back to the payer, but recurrence added a quieter obligation: the
invoice should not be able to change the recurrence timeline while still
looking like a response to the right request.

The first shape was too loose. An optional enum could describe the rough idea,
but it made the internal state feel more nullable than intentional. The final
three-way value was easier to reason about. `None` means an invoice must not
carry recurrence. `CreatedAt` means the first no-base recurrence should
establish its basetime from `invoice_created_at`. `Basetime(u64)` means a known
recurrence timeline already exists and the invoice has to preserve it.

The more important fix was moving where that expectation gets made. Deriving it
from `None` was fine scaffolding, but it ignored the information already
present in the invoice request. The request knows whether recurrence exists,
whether the offer supplied an explicit base, and whether this is the first
payment or a follow-up. Putting that logic into
`expected_invoice_recurrence_basetime` made the policy read from the same facts
the protocol is already carrying.

Verification stayed deliberately small after that. Metadata and `PaymentId`
checks still prove the invoice belongs to the request that was sent. The new
recurrence check only needs to answer one question: did the invoice use the
basetime the payer expected? That kept `verify_bolt12_invoice` on its existing
path for `OutboundPaymentForOffer`, with recurrence layered in as one more
constraint instead of a separate payment flow.

The tests had to be honest about the helper layer. Existing helpers can build
recurring requests for recurrence logic, but some of them mutate recurrence
fields after payer metadata has already been derived. That makes full metadata
verification the wrong target until the public recurrence payment API exists.
So the full invoice verification test stays on the non-recurring context path,
while the recurrence verifier gets direct coverage for the states that matter.
It is a smaller test shape, but it matches the boundary the stack actually has
today.
