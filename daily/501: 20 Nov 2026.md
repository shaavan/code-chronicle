# Log 501: Past the Window

> 20 November 2026

## What I worked on

- Added `UserConfig::enforce_recurrence_paywindow` on the
  [recurrence branch][continued], enabled by default. Applications can allow early
  or late automatic invoice responses while retaining authentication, recurrence
  state, schedule limits, and amount validation.
- Kept the policy in `OffersMessageFlow` through an `AtomicBool`, populated by
  `ChannelManager` during creation, restoration, and runtime configuration updates.
  Retained informational logging for accepted inbound timing exceptions; removed
  the outgoing logging helper and its extra timing calculations.
- Rejected initial proportional requests at or after their selected period ends,
  independently of paywindow enforcement. Both verification and invoice creation
  check this boundary; shared pricing arithmetic and received-invoice parsing
  retain their existing behavior.
- Simplified previous-state and first-request checks by inlining small conditions
  at their callers. Clarified configuration, proportional-pricing, and cancellation
  documentation, including why cancellation produces an event rather than an
  invoice.
- Fixed `set_current_config` reacquiring its own write lock by assigning through
  the existing guard. Formatting, compilation, and documentation checks passed
  during the work, including Rust 1.75 and `c_bindings`; behavioral tests were not
  run. The latest lock and documentation fixes remained uncommitted, with a revised
  commit message prepared.

## Reflection

Strict payment windows became awkward when I considered a recurrence that had
missed a period. Rejecting every late request could leave it unable to catch up.
Checking the draft's recommended timing behavior against its mandatory validation
left room for applications to choose a different policy. I first considered an
event that would hand invoice requests to the application, but that meant new
handling in both rust-lightning and LDK Node, on top of the recurrence tracking
Node already needs. A configuration flag was a smaller change I could see an
application using.

The flag needed a precise scope. Disabling it lets the automatic response path
issue an invoice outside the payment window; it does not decide when a payer
sends requests or when a payment settles. The other checks still apply, and LDK
Node still owns its recurrence database and overdue-payment tracking. Keeping the
policy in `OffersMessageFlow` also lets that flow operate independently of
`ChannelManager`, with the manager responsible for passing configuration through.
I kept the feature in a standalone commit while its place in the stack remained
open.

Allowing late requests exposed an uncomfortable edge of yesterday's joining
calculation. An initial request could select a fixed-anchor period that had
already ended, leaving no time to price and therefore a zero minimum. I briefly
considered rejecting every expired initial period, including non-proportional
offers. That reached further than the problem required. The automatic path now
rejects expired proportional joins, even when a custom paywindow extends beyond
the period or enforcement is disabled. It checks again at invoice creation so a
request cannot wait past the end and still receive its joining invoice.

I kept that rejection out of the arithmetic helper. Returning zero still describes
the time remaining, and changing it to an error would also reject received
invoices from other implementations. The issuance policy could stay local without
changing what generic parsing accepts. Late follow-ups and non-proportional
requests continue to use the configurable window policy.

The smaller cleanup took a few attempts too. Logging outgoing timing exceptions
needed a helper just to recover information that inbound validation already had.
I removed that machinery and kept the inbound log. The previous-state helper went
through borrowed fields and a move onto `RequestFields` before I accepted that
its small condition read better inline. The last review caught something more
concrete: the configuration setter took a write lock, then tried to take it again
for assignment. Reusing the guard fixed that and kept the stored configuration
and flow policy together. The commit message also needed another pass after
outgoing logging and zero-priced expired joins had disappeared from the code.
Those final corrections were ready to amend; behavioral coverage was still open.
