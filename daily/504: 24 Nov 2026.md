# Log 504: Before the Timer

> 24 November 2026

## What I worked on

- Made the timer reset explicit in the [static-invoice channel-update
  test][continued]. Checked that the tick sends no invoice when the offer is
  ready and its channel details have not changed.
- Moved the refresh decision ahead of peer and channel information collection.
  Nodes without a static invoice server now ignore refresh requests; repeated
  requests wait for the timer, and only immediate refreshes collect that data.
- Restored regression coverage checking that channel setup and repeated fee
  changes leave no refresh records before server configuration. Retained the
  existing checks for immediate refreshes and timer batching.
- Folded feature and test fixes into their respective commits without changing
  the final code. Compared `pr4758.07` with `pr4758.08` and prepared the reviewer
  update. Formatting and diff checks passed; tests were not run.

## Reflection

The channel-update test depended on a timer tick hidden inside an invoice
helper. Channel setup had already used the opportunity to refresh immediately,
and that incidental tick made the next update work as expected. Making it
explicit meant explaining why it belonged there and why it should send nothing:
the offer was ready, and the channel information had not changed. I spent some
time on that comment. The next person reading the setup should not need to
follow another helper to understand which state the test starts from.

The next review point found a case where waiting for the timer could never
help. A node without a static invoice server still recorded refresh requests,
but skipped the timer work that would clear them. It also gathered peer and
channel information before deciding whether there was anything to refresh.
Moving that decision earlier gave each case somewhere straightforward to go:
ignore the request without a server, wait for the timer after a recent refresh,
or collect the information needed to refresh immediately.

I added regression coverage, removed it during review, then restored it. The
serverless case deserved an explicit check alongside the existing immediate
refresh and batching checks. Channel setup and repeated fee changes should leave
no refresh records until a server is configured. Those assertions are back in
the test, though I have not run it. After folding the fixes into their owning
commits, the code stayed unchanged and the worktree was clean. A small setup
comment had led into a production path that was recording work it could never
process.
