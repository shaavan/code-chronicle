# Log 473: Keeping the Failure

> 05 October 2026

## What I worked on

- Replaced the optional active payment ID in the [recurrence implementation][recurrence-branch] with `RecurrencePaymentState`: `NoActivePayment`, `Active(PaymentId)`, and `Failed(PaymentId)`.
- Documented attempt state separately from recurrence lifecycle and placed the enum, initialization, and success transitions in their respective stack commits. Persisted-format compatibility still needs deliberate handling.
- Corrected the enum serialization declaration, used direct equality for active-attempt matching, and traced an invoice compilation error to an unnecessary `as_ref()` call and an FFI wrapper import.
- Added a terminal failure helper that checks for a unique active-payment match before persisting failure, requests event replay on persistence errors, and lets ordinary failure handling continue when duplicate matches are skipped in release builds.
- Ran formatting and whitespace checks, reverted unrelated formatter edits, and drafted the implementation commit message. Tests stayed unrun and the code edits remain uncommitted.

## Reflection

Clearing the active ID after failure had seemed enough in the earlier pass. Coming back to it, I wanted to keep the distinction between an idle recurrence and an attempt that had failed. The optional ID could tell me what was running, then lost that distinction once cleared. Keeping the failed payment ID in its own variant felt more honest. The attempt has ended, while the recurrence still has its own lifecycle; failure alone does not cancel it or advance the paid count.

That distinction gave the event handler a specific transition to make. It first collects every recurrence with the matching active ID, then changes state only when there is one result. A missing match needs no update, and duplicates leave recurrence state untouched. Matching the active variant also keeps a replayed failure from reaching a newer attempt. The persistence error still asks for replay, so the state check has to hold when the same event comes back.

I liked where the helper extraction ended up. Slice matching fit the vector the store already returns, and moving the block out of the handler made an early return less awkward: in release builds, a duplicate match exits the recurrence helper and ordinary payment failure handling carries on. The implementation now keeps the failed attempt visible, though changing the persisted field still leaves compatibility work to handle. Formatting and whitespace checks passed; the behavior still needs a test run.
