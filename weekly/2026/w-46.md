# Weekly Log 46: Where the Rules Belong

> 04 November 2026 – 10 November 2026

## Overview

The week opened with two existing branches needing another pass. Blinded-path
padding had to account for the length prefix it actually writes, and static
invoice refreshes needed a per-channel allowance so one noisy channel could not
delay another. Both changes needed examples that reached the behavior under
discussion and made its limits easy to follow.

After revisiting the OMv2 review, I returned to recurrence and began pulling the
larger branch into reviewable pieces. The offer model gave requirement, period,
anchor, window, and limit their own places. Request and invoice support then had
to preserve the distinctions those types depend on, from an explicit zero offset
to the timestamp that starts a schedule. Compilation covered the changed code,
but behavioral tests and authenticated state recovery remain ahead.

## Highlights

### Padding that fits and refreshes that wait

- Corrected the [blinded-path padding writer][padding-branch] to account for
  variable `BigSize` prefixes. Some gaps, including 255 and 256 bytes, cannot hold
  a valid padding TLV; path construction now advances the shared target by 30
  bytes until every forwarding hop can reach it exactly.
- Fixed the regression example's feature bytes so validation lets it reach the
  padding code. Extended coverage for large padding and both impossible gaps.
  Formatting, diff checks, and compilation of the library and tests passed;
  tests were not executed.
- Reviewed the [static-invoice refresh allowance][refresh-branch]. Each channel
  gets an immediate refresh for its first changed update between timer ticks;
  further changes wait for one deferred refresh. A shared budget could leave an
  honest channel waiting after another channel spent it.
- Expanded the update regression into explicit stages covering replay, repeated
  changes, deferred work, allowance reset, and a final idle tick. Kept checks for
  reuse of the server's original storage slot. Formatting and diff checks passed;
  tests were not run. Work still grows with distinct updated channels, and peer
  and channel collection happens before the throttle check.

### Narrowing the OMv2 review

- Revisited the [proposal review][omv2-review] against LDK's implementation,
  documentation, and tests. Offline-peer interception can retain messages until
  reconnection; authenticated dummy layers are unwrapped locally by the recipient.
- Proposed construction checks against known identities at a blinded-path
  junction, with the introduction node rejecting an immediate bounce hidden from
  the sender. Neither the sender nor the path creator can see the whole joined
  route during construction.
- Withdrew the missing-vector finding after checking the local copy and dropped
  the separate zero-padding validation comment. Retained questions about using
  more final-hop space for recipient context and handling unknown path IDs, plus
  the request to explicitly reject unsupported packet versions. No code changed.

### Carrying recurrence from offers into invoices

- Moved the [recurrence branch's offer model][recurrence-branch] into
  `offers/recurrence.rs`, with explicit defaults, nonzero period lengths, and
  nonzero bounded limits. Shared validation retains the
  relationships between fields; parsing also checks distinctions lost once
  absent TLVs become default values. Extended the TLV macros for module-qualified
  types in a separate prerequisite commit without changing encoding behavior.
- Proposed five PRs for offer terms, request and invoice fields, recipient
  handling, payer handling, and cancellation. Kept the tracking description
  explicit about completed offer work and the remaining stages. Corrected
  formatter guidance to Rust 1.85.0 while retaining Rust 1.75.0 compilation support.
- Adapted request fields for counter, start offset, previous state, and
  cancellation, preserving wire and persisted layouts. Separated request-local
  rules from offer compatibility checks and moved period selection into the
  offer commit. Refunds reject recurrence; public payment APIs remain deferred.
- Added invoice basetime and optional next state, then named the supporting
  structs `RequestFields` and `InvoiceFields`. Centralized basetime resolution in
  the request fields. Creation and parsing agree on recurrence presence, fixed
  anchors, and the first invoice's creation time for a first-invoice anchor.
  Refunds and static invoices reject recurrence.
- Removed a previous-state verification placeholder that always returned
  `Ok(None)`. Recovery plumbing remains, but later first-invoice-anchored requests
  still fail without a recovered basetime. Compilation included test code and
  no-std, with fuzz compilation during request work; documentation and formatting
  checks also passed. Later changes had no test execution or new coverage, and
  the final invoice edits remained uncommitted for incorporation into the stack.

## Reflections

The padding failure was a useful way to start the week. The shared target looked
reasonable until I followed the bytes written to reach it. Counting the real
prefix fixed one assumption, then exposed gaps no valid padding TLV could fill.
The example needed valid feature bits too. Each detail was small, but leaving
any one of them wrong would make the regression explain less than it appeared to.

I wanted the refresh test to be readable in the same way. A loop covered the
sequence compactly, but I kept having to decode its index to know whether the
allowance was being spent, deferred, or restored. Spelling out those stages made
the per-channel choice easier to judge. It also left the remaining cost visible:
the throttle limits repeated refreshes on one channel, while other work still
happens before that decision.

The OMv2 pass involved more subtraction. Some findings depended on an incomplete
local copy or an interpretation stronger than the draft supported. Dropping them
left questions I could describe more precisely, especially the bounce that only
becomes visible at the introduction node. I was more comfortable leaving fewer
comments once I could point to the implementation behind them.

Recurrence took most of the later work. Flattening the types made them easier to
inspect, but I had to keep checking what each field still needed to distinguish.
An absent start offset and `Some(0)` are different. Previous state can be present
and empty. Cancellation only needs presence. Those details decided which options
stayed and which representation could become simpler.

The invoice work then put a concrete timestamp behind the offer's anchor. A fixed
anchor already has one; a first-invoice anchor needs creation time initially and
authenticated recovery later. Removing the placeholder made that unfinished part
plain. The stack now has smaller pieces to review, with offer, request, and
invoice rules easier to follow across them. Next comes proving those rules in
tests and supplying the recovered state that later invoices need.
