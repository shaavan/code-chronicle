# Log 450: No Reply Needed

> 25 August 2026

## What I worked on

- Continued the recurrence stack from payer key derivation into the public
  `pay_for_recurrence` API shape.
- Kept `PaymentId` and `RecurrenceId` separate so payment attempts and durable
  recurrence relationships do not collapse into one identifier.
- Moved recurrence-specific payment inputs into their own params struct while
  leaving `amount_msats` as the invoice-request amount.
- Split cancellation into `RecurrenceCancellationParams` and
  `cancel_recurrence`, with no amount, retry config, or pending outbound
  payment state.
- Removed the reply path from cancellation requests and fixed receiver-side
  handling so verified cancellations can be recognized without a responder.
- Added payer and event coverage for no-reply-path cancellation, stable payer
  key derivation, missing outbound state, and invalid `counter == 0`.

## Reflection

Today moved recurrence from internal pieces into an API shape that has to be
honest about what the caller is doing. Paying for a recurring offer still looks
close to `pay_for_offer`: there is an amount, metadata, a reply path, and
eventual outbound payment state. But treating recurrence as only a variant of
offer payment would hide the part that matters most, which is the durable
relationship between the payer and the offer.

That is why the identifiers stayed apart. `PaymentId` names one attempt. It is
the thing outbound payment machinery already understands. `RecurrenceId` names
the recurring relationship, and it feeds the payer key derivation that has to
stay stable across requests. Letting one stand in for the other would make the
API smaller on paper, but it would also blur two lifetimes that need different
handling.

Cancellation made the boundary sharper. It travels through the invoice-request
encoding because that is where the recurrence proof lives, but it is not a
request for an invoice. There is no amount to pay, no retry configuration to
hold, and no pending outbound payment to track. Giving it
`RecurrenceCancellationParams` and a separate `cancel_recurrence` call made the
flow easier to read because the absence of payment state became part of the
API rather than a special case hidden inside payment setup.

Removing the reply path exposed a real handler mistake. The receiver required
a responder before it verified the invoice request, so the cancellation shape
that the payer was supposed to send could be dropped before the code had a
chance to see that it was a cancellation. Verifying first fixed that without
weakening the normal paths: cancellations can be classified without a
responder, while invoice and static-invoice requests still have to provide one.

The tests ended up being a useful check on the split. Payer-side cancellation
now proves the request has no reply path, creates no pending payment state,
uses the same recurrence payer key, and rejects a zero counter. Event-side
coverage uses the real no-reply-path flow instead of preserving the older test
shape with a responder. One targeted run was interrupted before completion, so
the verification story is not as neat as the final diff. The shape still feels
right: payment asks for an invoice, cancellation proves intent and stops
there.
