# Log 447: A Real Signal

> 19 August 2026

## What I worked on

- Continued the recurrence branch from handler gating into verified
  cancellation behavior.
- Added `Event::RecurringOfferCancelled` for cancellation requests that pass
  recurrence proof and paywindow checks.
- Chose `offer_id` and `payer_signing_pubkey` as the event identity instead of
  inventing an invoice-request id.
- Kept cancellation out of invoice creation so the handler emits no invoice
  response for that path.
- Added persistence and serialization coverage so unhandled cancellation events
  can survive restart.
- Tightened the local `agentss.md` commit guidance around when stack work
  should stay uncommitted.

## Reflection

Today was about turning the cancellation branch from a known gap into
something the rest of the stack can actually observe. Yesterday's handler work
left cancellation quiet on purpose. That was the right temporary shape, but it
also meant a verified `recurrence_cancel` request could pass all the important
checks and then fall into a TODO. The request was real enough to validate, but
not yet real enough to tell LDK Node what to remove.

The small design question that mattered most was identity. An `invreq_id`
sounded plausible for a minute because the cancellation arrives as an invoice
request. The code did not have that type, though, and it would have pointed at
the wrong thing. Recipient-side recurrence state is tied to the offer and the
payer relationship. The event now carries `offer_id` and
`payer_signing_pubkey`, which is enough for Node to find the state it owns
without making rust-lightning describe more of that storage model than it
needs to.

The implementation stayed on the verified cancellation path. A request still
has to get through recurrence proof and paywindow validation, but once it does,
the handler classifies it as cancellation work instead of invoice creation.
`ChannelManager` emits `RecurringOfferCancelled`, sends no invoice, and
persists the event with its own type. That keeps the protocol-facing signal in
rust-lightning while leaving durable recurrence removal where it belongs.

The stack needed the same care as the code. The first commit mixed feature
work and tests, which made the review unit too broad for this branch. Splitting
it back out helped the boundary read better: one commit adds the event,
identity fields, handling, and persistence; the next proves the verified path,
absence of invoice response, event identifiers, and serialization roundtrip.
Checking the feature commit on its own was a useful guard against letting the
test slice quietly prop it up.

That also fed a small cleanup in `agentss.md`. The phrase "work
conservatively" was still too soft around commits and history rewriting. After
spending the day moving the recurrence stack between mixed, split, squashed,
and split-again shapes, the local instruction needed sharper language: leave
changes uncommitted by default, commit only when asked, and treat labels like
"feat commit" or "test commit" as permission for that specific commit. The
code change was about making cancellation visible. The process change was
about making stack intent visible before touching history.
