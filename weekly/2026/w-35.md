# Weekly Log 35: Before the Handoff

> 29 August 2026 – 05 September 2026

## Overview

This week moved recurrence from a long upstream rebase toward an implementation
boundary LDK Node can actually own. It began with a smaller payment constraint:
dummy-hop fees must narrow the maximum without lowering the minimum the receiver
will enforce. From there, the recurrence stack returned to its own boundaries:
recovering a known commit position, correcting fixtures and bootstrap rules,
hardening cancellation and persistence, and finally deciding what belongs in
Node before the first implementation commit.

The rebase work kept exposing places where a compact helper or uniform fixture
was hiding a real distinction. Explicit-basetime offers need an initial start;
optional and implicit-basetime offers do not. A public recurrence helper should
remain public while flow arithmetic can use `payment_window`. Cancellation is
authenticated recurrence control, not an invoice request that happens to carry
no amount. LDK-only persistence fields need downgrade-compatible TLVs without
changing BOLT wire formats.

By the end of the week, the upstream side was stable enough to plan against.
The Node design now has explicit ownership for paid progress, amount limits,
automation, routing policy, durable lifecycle, recovery, and events. The work
ended before source changes, with the first commit ordered around the boundary
that the preceding review made visible.

## Highlights

### Keeping payment constraints in order

- Moved the payee minimum clamp after the dummy-hop fee loop while keeping the
  payee channel maximum before it.

- Added coverage showing that a `5_000` msat receive minimum stays `5_000`
  after three `1_000` msat dummy-hop fees, while the maximum is reduced.

- Removed the redundant no-fee BOLT 12 payment claim wrapper and kept the
  fee-aware helper under `claim_bolt12_payment`.

### Recovering the recurrence stack

- Rebased through Commit 13, adding explicit-basetime and original-start token
  coverage, then restored Commit 12's boundary tests after the rebase passed it.

- Kept the public recurrence helper during the Commit 11 conflict and used
  `payment_window` for flow arithmetic, preserving inclusive opening and
  exclusive closing semantics.

- Corrected fixtures for proportional pricing, replaced a private unchecked
  builder in test code, and supplied `start` only for explicit-basetime
  compulsory offers.

- Clarified that automatic payee flow means LDK-managed handling, then stopped
  at the Commit 14 conflict with the branch clean and the stack at a known
  boundary. ([Branch][rebase])

### Making cancellation and persistence hold up

- Allowed verified cancellation outside the payment window while retaining
  authentication, payer identity, recurrence continuity, and previous-state
  checks.

- Replaced an assertion on missing previous state with logged rejection, bound
  cancellation fan-out with the existing request limit, and verified that no
  reply path or pending payment state is created.

- Moved LDK persistence-only recurrence fields to skippable odd TLV types while
  leaving BOLT wire formats unchanged, with current and legacy reader coverage.

- Assigned corrections and regression coverage to their final commits across
  the 24-commit stack, including the nonzero `RecurrenceLimit` documentation
  fix. ([Branch][recurrence])

### Giving Node a real starting boundary

- Reviewed the corrected Node handoff against the pinned rust-lightning revision
  and confirmed no upstream blocker to implementation.

- Put recurrence methods on the existing BOLT 12 payment handler, with
  caller-selected initial periods, opt-in automation, and manual payment kept
  as separate behavior.

- Defined exact amount authorization for amountless offers, fixed recurrence
  inputs, terminal-record retention, and removal only when no attempt is
  pending.

- Separated fixed protocol state from mutable routing and retry policy, then
  ordered durable acceptance, restart recovery, lifecycle events, Rust APIs,
  UniFFI bindings, scheduling, cancellation, tests, and docs.

## Reflections

The week kept returning to ordering. In the dummy-hop path, the order of the
fee loop and the receive minimum clamp changed whether a valid payment could
reach the receiver. In recurrence, the order of commits, fields, and lifecycle
operations changed whether the design still described the protocol it was
trying to support.

The rebase made those distinctions hard to avoid. A fixture that supplied
`start = 0` everywhere looked convenient until the compulsory and optional
basetime rules were read together. A test helper calling a private unchecked
builder looked harmless until the public test surface was considered. The
conflicts were useful because they forced each correction back toward the
commit where its assumption first appeared. Aborting at Commit 14 left less
finished code, but a branch whose next boundary was understood.

Cancellation then tested whether the protocol boundaries held under hostile or
late input. The payment window controls when an invoice can be paid. It does
not decide whether a verified request to cancel a recurring relationship is
meaningful. The same separation showed up in the message limit, the missing
previous-state rejection, and the odd persistence TLVs: untrusted input needs
bounded handling, and local storage extensions need to remain invisible to
older wire-level readers.

The final Node plan started with a possible upstream blocker. The payment
handler queues its invoice request before inserting pending-payment state, so a
duplicate payment id can fail after queuing. The ordinary offer-payment path
already has that ordering, which meant recurrence did not need to invent a new
prerequisite before Node could begin. That left the real design work where it
belongs: Node owns paid progress, durable records, scheduling, recovery, and
lifecycle delivery; rust-lightning owns protocol validation and payment
mechanics.

The first implementation commit now has a precise place to start. Durable
intent comes before submission, manual progression before scheduling, recovery
before automation, and native Rust APIs before their UniFFI surface. The week
did not produce Node source, but it removed enough ambiguity that the first
source change will be testing an owned design rather than discovering one.
