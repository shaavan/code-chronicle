# Log 487: Onion Message 2.0

> 29 October 2026

## What I worked on

- Read BOLT PR #1367 and mapped Onion Message V2 onto rust-lightning and LDK
  Node for an [implementation tracking issue][omv2-tracker]. Most work belongs
  in rust-lightning, with downstream adoption and mailbox compatibility in
  LDK Node.
- Examined the fixed routing header, eight routing slots, and separate
  encrypted payload. Reviewed the Python reference implementation and vector
  generator, and saved a local specification copy verified against the
  upstream blob checksum.
- Organized implementation milestones from packet primitives and transport
  through routing, applications, and release validation. Kept relay support
  separate from complete BOLT12 invoice-request and invoice-reply flows.
- Narrowed spec-review questions to the visible-prefix/blinded-tail junction,
  disconnected-peer forwarding, and locally peeled dummy hops. Kept compact
  path size, application audits, and retry behavior as implementation work.
- Condensed the personal checklist into a public tracking issue. Authenticated
  context and BOLT12 path integration remain design questions; implementation
  and protocol validation are still ahead.

## Reflection

I started by trying to understand how much of the existing onion-message code
could carry forward. The cryptographic primitives, route blinding, Sphinx
construction, and handlers give OMv2 somewhere to begin, though the packet and
payload work is substantial. The fixed routing slots made the path bound
concrete after the earlier parameter discussion. Reading the reference code
and generated vectors also gave the eventual Rust tests something independent
to check against.

The first tracker grew into a checklist I could have used while implementing
the feature. Making it useful to other contributors took another pass. Some
of the questions were still things I needed to investigate in LDK. DNS
resolution, async payments, custom messages, and retries all need an audit,
but I had not found a specific incompatibility that required an upstream
answer. Moving those into implementation tasks made the remaining questions
easier to discuss.

The blinded-path case took more thought. I was comfortable treating a
recipient's `blinded_path_v2` as reasonable assurance that its chosen hidden
nodes support OMv2. The awkward part was where the sender adds a visible
prefix. Alice could prepend Bob to a path starting at Carol without knowing
that Carol's hidden next hop is Bob. Carol has to reject that bounce, yet the
parties constructing the route may lack enough information to avoid it.
That left a precise question about what the writer is required to guarantee.

The mailbox comparison found a more direct wording problem. OMv1 does not
explicitly require dropping a message when its next peer is disconnected;
LDK's optional interception lets LDK Node retain it for later delivery. OMv2
explicitly says to ignore it. Whether deferred forwarding is intended to be
prohibited needs an answer before mailbox adoption can be planned. Dummy
hops had a similar distinction: peeling them locally avoids asking other
implementations to understand them, but still has to satisfy the prohibition
on consecutive identical nodes. Compact paths raised a different concern.
Losing SCID-based encoding to full node IDs needs a size assessment,
particularly for offers carried in QR codes.

By the end, I had fewer questions in the discussion section and more definite
work in the checklist. Forwarding a packet can be an early milestone without
claiming the BOLT12 exchange works. The three spec-review points now have
specific cases behind them, while authenticated context and path integration
still need design work. I can begin from that plan without needing every
application detail settled first.
