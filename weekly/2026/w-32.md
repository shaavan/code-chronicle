# Weekly Log 32: Reviewable Ground

> 11 August 2026 – 13 August 2026

## Overview

This week stayed with BOLT 12 recurrence, but the work moved from broad
feature pressure into a smaller review shape.

The first pass was mostly about deciding where the feature should live.
rust-lightning needs to own the protocol surface: recurrence TLVs, parsing,
serialization, period calculation, invoice-request validation, invoice
recurrence fields, and the state handoff between
`invoice_recurrence_next_state` and `invreq_recurrence_prev_state`. LDK Node
needs to own the durable wallet behavior around recurring payments: storage,
scheduling, replay, cancellation, and user-facing APIs. Writing that split
down made the branch feel less like one large recurrence object and more like
a set of responsibilities that can be reviewed in order.

The middle of the week cleaned up the API shape before that shape became
expensive. `Recurrence` stopped being an enum with duplicated payload fields
and became a struct carrying the shared period, paywindow, and limit directly.
`RecurrenceType` stayed as the discriminator for compulsory versus optional
recurrence. That kept the wire encoding the same while making validation and
callers stop matching through two variants just to reach the common fields.

The week ended by turning the top of the stack into a first WIP PR. Reading
the six commits as a standalone slice exposed one missing public edge:
`Bolt12Invoice` could parse invoice recurrence, but callers could not inspect
it. Adding the `invoice_recurrence()` accessor and paired parsing tests made
the invoice feature surface match the data already moving through the parser.
The PR now shows the message shape without pulling in the heavier recurrence
state generation work too early.

## Highlights

### Splitting recurrence by ownership

- Turned the recurrence work from a broad protocol read into a concrete issue
  structure across rust-lightning, LDK Node, and spec interop.

- Separated rust-lightning work into wire fields, parsing, validation, period
  helpers, invoice-request builder support, and handler behavior.

- Drew the line between protocol checks that belong near BOLT 12 messages and
  durable recurring-payment behavior that belongs in LDK Node.

- Kept the issue language aligned with the draft names:
  `invoice_recurrence_next_state` and `invreq_recurrence_prev_state`.

### Making recurrence easier to use

- Replaced the duplicated `Recurrence` enum payload with a struct that carries
  shared recurrence fields directly.

- Kept `RecurrenceType` as the smaller discriminator for compulsory and
  optional recurrence, including compulsory basetime handling.

- Updated offer parsing, serialization, and tests around the new structure
  without changing the protocol encoding.

- Carried the API shape through invoice-request validation and invoice
  basetime logic, then checked for stale enum-style usage. ([Branch][recurrence])

### Preparing the first review slice

- Read the top six recurrence commits as a standalone sequence for the first
  WIP PR.

- Checked that the stack split cleanly across offer, invoice-request, and
  invoice recurrence feature commits with adjacent tests.

- Added the missing public `invoice_recurrence()` accessor for parsed invoice
  recurrence data.

- Covered recurring and non-recurring invoice parsing paths so the accessor is
  tested for both `Some` and `None`.

- Left `invoice_recurrence_next_state` wired as a field while keeping actual
  recurrence-state creation and verification for the next slice. ([PR][wip])

## Reflections

The useful part of the planning work was that it made recurrence smaller
without hiding any of the hard parts. The protocol layer still has to parse
the fields, check counters, respect payment windows, carry previous and next
state, and reason about calendar periods that do not collapse into fixed
durations. That is enough work on its own. Letting rust-lightning also become
the place that stores a user's recurring payments or wakes up on a schedule
would make the boundary blurry in a way the protocol code could not really
honor.

The API cleanup came from the same pressure. Recurrence has a lot of moving
pieces already, so a shape that forces callers to match through compulsory and
optional variants just to read period or paywindow adds friction in the
wrong place. Making the shared fields direct did not make the feature simpler
than it is. It made the common case less awkward, and it left the distinction
between compulsory and optional recurrence where that distinction matters.

The rebase made this more careful than a straight cleanup would have been.
Each change had to land in the commit where the public surface or parser shape
first appeared. That forced the branch to tell a more honest story: offer
support first, invoice-request support next, invoice support after that, with
tests close enough to each feature commit to explain what changed. The missing
invoice accessor was easy to miss in code because the parser already carried
the data, but it would have been obvious to any caller trying to use the
feature.

The decision to leave recurrence-state generation out of the first PR felt
important. `invoice_recurrence_next_state` has a place in the invoice, and the
parser can expose it, but deciding how that state is created and verified is a
larger design question. Pulling it into the first review slice would make the
PR harder to read and would weaken the line between field support and behavior
that needs its own tests.

By the end of the week, recurrence had a firmer review path. The first slice
can ask reviewers to look at the message surface, public accessors, and parser
coverage. The next slice can then deal with the state machine pressure
directly, instead of being buried inside the first pass at making the fields
exist.
