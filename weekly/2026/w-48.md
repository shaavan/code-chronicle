# Weekly Log 48: The Lifecycle of Software Objects

> 19 November 2026 – 25 November 2026

## Overview

The recurrence APIs were in place, but following requests through them kept
finding assumptions that needed another look. Joining partway through a period
needed a price calculated at invoice creation. Accepting a late request needed
an application policy. Returning from manual invoice handling needed enough
schedule information, which did not always mean returning a token.

The other reviews brought similar questions to smaller pieces of code. A static
invoice refresh could record work on a node that would never process it. A
currency invoice could be signed at an amount that disagreed with its request.
The dummy-hop privacy report needed several invoices before its weakness became
visible. Each review meant following behavior beyond the case I first had in
mind. Build and documentation checks passed where run; behavioral tests remain
open, and the privacy assessment stayed source-based.

## Highlights

### Pricing a join and allowing late requests

- Implemented proportional pricing on the [recurrence branch][recurrence-branch]
  for initial requests joining a period partway through. Quantity is applied
  before scaling, arithmetic is widened, and the result rounds up to whole
  millisatoshis. Follow-ups retain the full-period price.
- Separated preliminary request checks from the minimum resolved at invoice
  creation. Construction and parsing use the invoice's creation timestamp, and
  automatic response validation returns the amount to use. Offer expiry prevents
  starting a recurrence while permitting follow-ups and cancellation afterward.
- Added `UserConfig::enforce_recurrence_paywindow`, enabled by default, with
  configuration passed into `OffersMessageFlow` at creation, restoration, and
  runtime updates. Disabling it permits early or late automatic responses while
  retaining authentication, state, schedule limits, and amount checks. Fixed the
  configuration setter reacquiring its own write lock.
- Kept expired proportional joins outside that policy choice. Verification and
  invoice creation reject them at or after the selected period ends, even with
  enforcement disabled. Generic arithmetic still returns zero for an ended
  period, and received-invoice parsing retains its existing behavior.

### Letting the schedule determine what state is needed

- Removed blanket previous-state requirements. Fixed-anchor follow-ups can use
  the offer's basetime; first-invoice-anchored follow-ups still need the original
  basetime recovered. Supplied tokens remain authenticated, and cancellation can
  omit state. Tokens do not prove earlier payment.
- Made cancellation amount access safely return `None` when absent. Direct
  responders reject attempts to create payable cancellation invoices, and parsing
  rejects received invoices answering cancellations. Direct responders retain
  caller-owned timing policy.
- Folded review and paywindow fixes into their owning commits, leaving a clean
  fourteen-commit stack. Removed the local payment-ID reservation fix so the
  recurrence and ordinary payment APIs can be corrected together upstream.
  Formatting, diff, Rust 1.75, C bindings, and relevant documentation checks passed
  during the work; tests were not run.

### Comparing invoices for privacy

- Reviewed the [dummy-hop privacy report][privacy-report] against the source.
  Fresh dummy fees and CLTV deltas can stand out across invoices when real
  forwarding policies stay stable. The resulting inference concerns dummy-hop
  count and the real route's aggregate CLTV contribution; it does not uniquely
  reveal the real hop count.
- Compared stable padding per route, stable padding per offer, and standardized
  aggregate totals. Each leaves sampling or invoice-linking questions, or adds
  fee and timelock costs. Prepared a discussion draft without selecting a
  mitigation. The reproducer was not run; neither fund theft nor payment failure
  was demonstrated by the report.

### Checking refresh work and agreed amounts

- Moved the [static-invoice refresh decision][refresh-branch] before peer and
  channel information collection. Nodes without a server ignore refresh requests;
  repeated requests wait for the timer. Made the test's allowance-reset tick
  explicit and restored assertions that serverless channel setup and repeated fee
  changes leave no refresh records. Formatting and diff checks passed; tests were
  not run.
- Clarified that callers migrating to `pay_for_bolt12_invoice` must check amounts
  with `Bolt12Invoice::verify_amount_acceptable_for_payment` on the
  [currency branch][currency-branch]. Added shared builder validation rejecting
  disagreement with an explicit request amount, with coverage for matching,
  lower, and higher values across bitcoin and currency offers and both signing
  strategies. Requests without explicit amounts remain unchanged.
- Documented the new builder amount argument, application-owned cached-rate
  freshness, and conversion failures becoming `UnsupportedCurrency`. Removed
  conversion guidance for amountless async offers. Rebased the eleven-commit
  stack across 796 upstream commits, resolving API and test compatibility issues.
  Formatting, diff, workspace, test-target, and fuzz compilation checks passed;
  tests were not executed.

## Reflections

Proportional pricing took more work around the calculation than inside it. The
request can arrive before its final price is knowable, and it can wait long
enough for both that price and its eligibility to change. Using invoice creation
time gives construction and parsing the same answer. Allowing late responses
then exposed the zero-priced join into a period that had already ended. Keeping
that rejection in issuance policy let the arithmetic continue describing the
remaining time without imposing our response policy on received invoices.

The token requirement needed a different kind of correction. Last week I had
followed the automatic flow closely enough that every follow-up seemed to need
its previous invoice's state. A manually created invoice without `next_state`
made that requirement feel awkward. For a fixed anchor, the offer already has
the basetime; requiring a token would block a handoff the schedule can support.
First-invoice anchors still need their original timestamp recovered. Working
through those cases gave me a better reason for each rejection than requiring
state everywhere.

The privacy review resisted a similarly quick answer. Fresh random padding can
be recognizable when the real route stays stable, but making it stable introduces
questions about linking invoices. I could describe the weakness more precisely
after comparing those choices, without having a mitigation I was ready to pick.
The report also needed to keep its limits: an aggregate CLTV estimate does not
uniquely reveal the number of real hops.

I liked the smaller fixes later in the week. An explicit timer tick made the
refresh test easier to read, then the review found records accumulating where
no server existed to clear them. Following the currency amount caught a mistake
before signing as well as a check callers could lose during migration. The
rebase was larger, and compilation found compatibility problems that merged
without conflicts. Those checks got the stacks back into shape. Next I need to
run the paths they describe, especially timed joins, tokenless handoffs, and the
new amount and refresh assertions. The shared payment-ID ordering fix still
needs to be handled across both payment APIs.
