# Log 469: What Belongs Here

> 24 September 2026

## What I worked on

- Reviewed the [recurrence dependency-plumbing commit][recurrence-branch] across dependency updates, serialization-macro renames, payment variants, and payee-key recovery.
- Reconsidered proposed tests for recurrence events, FFI invoice recovery, unified-payment fallback, and public cancellation handling.
- Kept the test coverage that checks legacy peer-store, custom-TLV, and wallet address-pool data remains readable after the macro migration.
- Removed an unused VSS test import and identified stale `lib.rs` imports left by the discarded event-handler test.

## Reflection

The review started with a long list of tests suggested by the visible changes in the dependency-plumbing commit. Looking at what the commit actually owns reduced that list quickly. Recurrence storage and management do not exist yet, so persistence and handler tests would have described behavior belonging to the later feature work. Emitting a public cancellation event before its consumer exists would have the same problem.

The FFI and unified-payment proposals fell away for different reasons. Payee-key recovery already exists in LDK-Node, and the wrapper delegates to LDK, so rebuilding invoice tests here would repeat upstream coverage. The unified-payment cases did not prove useful behavior: one inferred fallback from `Error::NotRunning`, while the other only confirmed unsupported-method failure.

Legacy serialization fixtures were the part worth keeping. A mechanical macro migration can still break data that was already persisted, and peer-store, custom-record, and address-pool fixtures test that boundary directly. The smaller set says more than a fixture for every type when the complete `PeerStore` path already includes `PeerInfo`. The commit is now easier to review because its tests match compatibility work it can actually own.
