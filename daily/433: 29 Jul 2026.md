# Log 433: Keeping the Boundary

> 29 July 2026

## What I worked on

- [Continued] the currency-payment branch by removing currency-conversion
  plumbing from the async static-invoice path.
- Split the reviewer feedback into the current cleanup and a follow-up rule
  that amountful static invoices should be rejected explicitly.
- Removed the converter from async receive offer creation,
  `static_invoice_received`, and the `ChannelManager::initiate_async_payment`
  call into that path.
- Replaced static-invoice receive-side amount handling with local bitcoin-only
  derivation while leaving ordinary BOLT12 invoice currency conversion intact.
- Cleaned up stale tests and docs that still described currency-denominated
  async static-invoice payments as supported.

## Reflection

The currency branch needed a smaller answer than the one it had been carrying.
The reviewer point was not that static invoices needed better conversion
handling. It was that static-invoice offers should not be asking the currency
converter a question in the first place. Amountful static invoices are odd
enough to reject directly, but that is a validity rule, not a reason to keep
conversion state threaded through async receive.

That split shaped the day. The current PR could remove the conversion
machinery from the async static-invoice flow, and the explicit rejection rule
could follow in its own patch. Keeping those two pieces apart made the code
easier to reason about. The branch was no longer trying to both define an
invalid shape and clean up a path that should not depend on it.

The edits followed the call chain. Async receive offer creation moved to
`NullCurrencyConversion`. `OutboundPayments::static_invoice_received` stopped
accepting a converter. `ChannelManager::initiate_async_payment` stopped
passing `self.currency_conversion` into that path. The receive-side amount
calculation became local and bitcoin-only, while the normal BOLT12 invoice
path kept the conversion logic it still owns.

The rebase made the boundary visible in a useful way. Later commits kept
trying to reintroduce conversion state into `static_invoice_received`, because
that was how the stack had been shaped before. Resolving those conflicts was
less about choosing one side of a diff and more about making the same rule
hold across the stack: static-invoice receive should not have conversion
state; regular invoice handling still should.

The tests had to say the same thing. Some old coverage still assumed
currency-denominated async static-invoice payments were part of the supported
surface. Adjusting those tests would have kept the wrong contract alive, so
they were removed. The remaining currency tests stay on ordinary BOLT12
invoice verification, where the payer and recipient still need the converted
amount checks.

I liked the final shape because it made the PR less ambitious in the right
place. The branch now answers the conversion part of the review without hiding
the amountful static-invoice question inside it. That follow-up still matters,
but it can be written as a direct rule instead of as a side effect of cleaning
up a call chain.
