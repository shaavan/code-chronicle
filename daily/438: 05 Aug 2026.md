# Log 438: Less Provisional

> 05 August 2026

## What I worked on

- [Continued] the recurrence branch by reading the draft shape around offers,
  invoice requests, and invoice-returned recurrence state.
- Fixed the offer recurrence feature commit for broken rustdoc links,
  speculative source commentary, and trailing whitespace.
- Moved an `offer_recurrence` rename out of the test commit and back into the
  offer feature commit where it belonged.
- Tightened recurrence period coverage with end-of-month and leap-year cases
  for monthly behavior.
- Reworked invoice-request recurrence around the draft's
  `invreq_recurrence_prev_state` field and added refund rejection coverage for
  that field.

## Reflection

The recurrence branch started with a spec-reading pass because this work is too
easy to get wrong by following the shape of the old commits alone. The draft
has a particular rhythm: offers advertise optional or required recurrence,
invoice requests carry their counter and state echo, and invoices hand back
state for the next request. Once that was in view, the review work became less
about naming everything generally and more about making each commit line up
with the field it was actually introducing.

The offer-side commit mostly needed source hygiene. Broken rustdoc links,
trailing whitespace, and a little public-source speculation are small things,
but they make an early protocol commit feel less settled than it should. The
tests stayed in the following commit because the stack already has that
feature-then-test shape, and keeping that boundary clean mattered more than
pulling all related changes into one patch.

That boundary caught a real ordering issue next. The rename from `recurrence`
to `offer_recurrence` had landed with the tests even though it changed the
feature surface. Moving it back into the offer commit made the test patch read
like coverage again. The month-period cases also needed more than the happy
path. End-of-month and leap-year behavior are exactly where calendar recurrence
stops being a simple duration, so the tests had to pin that down instead of
only proving a mid-month example.

The invoice-request side had more of the draft still showing through. A public
recurrence API that cannot be constructed outside the crate is not really a
public API. The previous-state field also still carried provisional `token`
language and the wrong TLV type. Renaming it to
`invreq_recurrence_prev_state`, moving it to `type 96`, and teaching refunds
to reject it made that part of the branch feel much closer to the spec text
instead of an intermediate sketch.

The last pass was mostly about making the tests catch up with the feature
shape. They still built private `token` fields and mutated the old TLV name,
which meant they were protecting yesterday's implementation more than today's
API. Switching them to public constructors and accessors was a small but useful
pressure test. Adding the refund case for `recurrence_prev_state` closed the
other hole, because a field that belongs to invoice requests should not slip
quietly into refunds.

By the end, the branch had fewer provisional names and fewer commits carrying
work from the wrong layer. That matters on a protocol stack. The code can be
right in isolation and still be hard to review if the commit history blurs
whether a change belongs to the data model, the tests, or the follow-up fixup.
Today was mostly making those lines hold.
