# Log 463: Holding the History

> 12 September 2026

## What I worked on

- Reviewed the 33-commit recurrence stack with its autosquash targets and history in view.
- Inlined the single-use cancellation-event helper, removed its pass-through test, and separated test-documentation changes into the commits they belonged to.
- Dropped outbound-amount changes that broadened payment behavior beyond recurrence requirements, restoring the original invariant.
- Replaced the local `RecurrenceId` wrapper with rust-lightning's upstream type while retaining Node-specific storage and hexadecimal handling.
- Fixed serialization and import compatibility issues, then compiled the stack with Cargo 1.98 and traced the missing-import fixup to the commit that removed it.

## Reflection

The recurrence work was already large enough that reviewing [the recurrence stack][recurrence-06] meant looking at two things at once: whether the code held together, and whether each change still belonged where it had been placed. A single-use helper did not need its own abstraction. Test comments made more sense beside the persistence coverage they explained. Moving those changes into top fixups left the eventual history easier to read without changing the behavior.

The amount-handling review found a more consequential boundary. Recording the amount from LDK's `PaymentSent` event supports variable-amount recurring BOLT12 payments, but removing an existing `expect` introduced a wider fallback than recurrence needed. Dropping that implementation and its dependent tests restored the invariant instead of making ordinary outbound payments absorb recurrence-specific uncertainty.

Replacing the local `RecurrenceId` wrapper with rust-lightning's type exposed the kind of coupling that is easy to miss while a stack is growing. Updated serialization macros made optional fields reject old `.0` accesses, and the external-to-external conversion no longer made sense once the upstream type was used directly. The compiler found those seams quickly. Cargo 1.75's lockfile error was a toolchain mismatch; Cargo 1.98 compiled the stack with only the existing dead-code warnings.

History then answered the last question. `[feat] Handle failed recurrence attempts` (`360be9d3`) had removed `RecurrenceAttempt` from the import list even though earlier successful-payment code still used it. The missing-import fixup belongs there, rather than beside the successful-payment change. By the end, the stack was compilable and its cleanup had a place in the history that matched the reason for the change.
