## Reflection

Today turned on whether the first recurrence slice could be reviewed on its
own terms. The branch had already gone through the larger API reshaping, and
the six commits at the top had a reasonable outline: offer support,
invoice-request support, invoice support, and tests sitting next to each
piece. Reading them as a PR made the remaining awkwardness easier to see.

The real gap was small in code but large in API shape. `InvoiceRecurrence`
existed, and the parser could carry the invoice recurrence TLVs through, but
`Bolt12Invoice` did not expose the parsed object. That would have left callers
with a feature they could receive but not inspect. Putting
`invoice_recurrence() -> Option<&InvoiceRecurrence>` into the invoice feature
commit made the public surface match the data being parsed.

The rebase made the work feel more careful than direct. The stack was stopped
inside earlier commits, so the first pass stayed with the offer commit and
cleaned up the message details there. The accessor waited until the rebase
reached `[feat] Introduce invoice recurrence`, where it belonged. The tests
then landed in the paired parsing commit, checking both the positive recurrence
case and the `None` case for non-recurring invoices. That kept the stack from
turning into a pile of fixes at the end.

The other boundary was the next-state field. The invoice is the right place to
hand state back to the payer, but generating and verifying that state is more
than a field wiring change. Leaving production invoice creation with
`InvoiceRecurrence::new(recurrence_basetime, None)` is a narrow choice, but it
keeps this PR honest. It shows where the state will live without pretending
the recurrence-state design is already done.

By the end, the branch felt ready to put in front of reviewers. The first PR
does not finish recurrence, and it should not try to. It gives the messages a
shared reviewable shape, exposes the invoice-side data through the public API,
and leaves the next thread clear: actual recurrence-state creation and
verification.
