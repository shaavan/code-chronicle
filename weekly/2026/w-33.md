# Weekly Log 33: The Handoff Holds

> 15 August 2026 – 20 August 2026

## Overview

This week stayed inside BOLT 12 recurrence, but the work moved from field
support into the behavior that lets recurrence survive one payment and become
the next request.

The first part of the week narrowed `invoice_recurrence_next_state` into a
stateless continuity token. The useful boundary was that rust-lightning can
prove a follow-up request belongs to the same offer, payer, counter, start,
and payee key material without storing a subscription. That kept the token
honest without pulling in payer APIs, cancellation storage, or scheduling
policy before they had a shape of their own.

Once the token existed, the next pressure was where it should be produced.
Keeping the public invoice response methods unchanged made the flow feel more
like an extension of verified invoice creation than a new recurrence-specific
API. `OffersMessageFlow` now has the context to create the nonce, derive next
state, attach invoice recurrence, and reject requests whose previous state or
paywindow does not hold.

The handler work then split recurrence into the two paths it needed: accepted
requests produce invoices with next state, and verified cancellations produce a
real event. `RecurringOfferCancelled` gives LDK Node the offer and payer
identity it needs to remove durable state later, while rust-lightning stays
focused on proving that the cancellation request is valid.

The week ended on the payer side. The reply path now records what recurrence
basetime an invoice is allowed to carry, and invoice verification checks that
expectation alongside the existing metadata and `PaymentId` checks. That made
the recurrence handoff two-sided: the payee can verify continuity before
issuing the next invoice, and the payer can reject an invoice that moves the
timeline it asked for.

## Highlights

### Proving recurrence without storage

- Scoped `invoice_recurrence_next_state` to internal creation and verification
  rather than public recurring-payment behavior.

- Built the state token around offer id, payer signing key, recurrence counter,
  start, and payee key material.

- Added direct validation coverage for successful handoff, mismatched inputs,
  malformed state, and overflow behavior.

- Kept cancellation, proportional amount policy, public payer APIs, and
  ChannelManager response behavior outside the state-token slice.

### Carrying next state through invoice creation

- Moved next-state issuance into `flow.rs`, where verified recurring requests
  already have the context needed for invoice construction.

- Kept the existing `respond_*_no_std` public response methods instead of
  adding recurrence-specific variants.

- Tied invoice recurrence basetime and next-state token derivation to the same
  `created_at` value.

- Updated invoice-creation tests to build recurring requests, attach next
  state, and reject missing previous state or counter overflow.

### Keeping handler behavior narrow

- Left recurrence acceptance inside `OffersMessageFlow` instead of adding a
  new recurrence decision layer to `ChannelManager`.

- Added a defensive invariant check for previous recurrence state, with debug
  builds made loud if verified metadata reaches an impossible branch.

- Fixed handler tests to send recurring invoice requests through the offer's
  blinded path with recurrence present before metadata derivation.

- Added `Event::RecurringOfferCancelled` for verified cancellation requests
  that pass recurrence proof and paywindow checks.

- Persisted cancellation events and covered their serialization roundtrip.

### Checking the payer's expected basetime

- Added reply-path recurrence basetime expectations to `MessageContext`.

- Moved expectation construction into the invoice-request path, where
  recurrence shape, explicit offer basetime, and follow-up state are visible.

- Kept payer-side invoice verification narrow by checking invoice recurrence
  basetime on top of existing metadata and `PaymentId` validation.

- Covered absent recurrence, `invoice_created_at` basetime, known basetime, and
  mismatched basetime in direct verifier tests. ([Branch][recurrence])

## Reflections

The useful pattern this week was adding behavior only after the boundary around
it was small enough to defend. Recurrence can easily turn one helper into the
place where the whole product model leaks in: subscriptions, cancellation,
retry policy, proportional amounts, storage, and user-facing APIs all sit
near the same code. The branch got more stable each time one of those concerns
was named and then left out of the current commit.

The state token was the clearest example. It would have been possible to make
the payee remember more, but the protocol did not need that to prove
continuity. Letting the invoice hand back an opaque token, and letting the next
request return it with the counter and recurrence start, kept the payee-side
promise concrete. The tests around wrong offers, wrong payers, wrong counters,
wrong starts, wrong key material, malformed state, and overflow gave that
stateless shape something firmer than a design preference.

Invoice creation had a different kind of pressure. The first response API made
recurrence too prominent at the call site, as if every invoice response needed
to choose a recurrence-specific method. Pulling the work back into
`OffersMessageFlow` fit better with the rest of the stack. A verified
recurring request still becomes an invoice through the ordinary response path;
the flow attaches next state only when the request proves it belongs there.

Cancellation needed the opposite movement. Leaving it silent was fine while
the handler shape was still unsettled, but once recurrence proof and paywindow
checks existed, silence became less honest. The event does not pretend
rust-lightning owns durable recurrence state. It gives Node the two identifiers
that matter for its storage model and keeps invoice creation out of the
cancellation path.

The payer-side basetime check made the handoff feel less one-directional.
Before that, most of the work protected the payee from invalid follow-up
requests. The reply path now also protects the payer from an invoice that
answers the right request while quietly moving the recurrence timeline. That
is a small verifier change, but it makes the recurrence sequence easier to
trust from both ends.

By the end of the week, recurrence had moved from parsed fields into a more
complete protocol loop: create next state, verify previous state, gate handler
behavior, signal cancellation, and check the payer's expected basetime. The
remaining work still has weight, especially public payer behavior and durable
Node-side handling, but the protocol side now has enough internal structure
for those pieces to attach without asking rust-lightning to become the wallet.
