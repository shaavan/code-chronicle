# Weekly Log 29: No Private Shape

> 21 July 2026 – 25 July 2026

## Overview

This week stayed mostly with dummy-hop review work, with one day spent reading
the recurrence spec and pulling on the longer-lived state it would ask wallets
and payees to carry.

The dummy-hop branch kept narrowing around the same privacy question: when a
padded blinded path is inspected through normal forwarding rules, what still
looks invented? Earlier work had made generated relay policies more realistic,
but review found that payment constraints still carried sentinel values. A
dummy hop with believable fees can still stand out if its `htlc_minimum_msat`
and `max_cltv_expiry` do not look like ordinary forwarding bounds.

That pushed the fix away from better defaults and toward better construction.
Complete dummy TLVs now need downstream payment constraints before they can be
built. The code walks backward through dummy relays the same way real blinded
path construction walks backward through forwarding hops, and tests compare
the two directly. The recurrence reading raised a nearby concern at protocol
scale: long-lived offers need proof, reachability, and time anchors that still
make sense after the first request has gone stale.

## Highlights

### Making dummy constraints part of construction

- Changed dummy-hop TLV construction so payment constraints are derived
  backward from the payee's downstream max CLTV and each dummy hop's CLTV
  delta.

- Removed `DummyTlvs::default()` and `DEFAULT_DUMMY_PAYMENT_CONSTRAINTS`, so a
  complete dummy TLV can no longer exist without downstream context.

- Reworked the blinded-payment test helper to carry only the local dummy-hop
  count instead of passing complete dummy TLVs with fake constraints.

- Kept `default_relay()` as the deterministic relay-policy fixture while
  making production-random and deterministic test construction pass through
  the same constraint derivation path.

### Checking whether padding looks ordinary

- Focused review work on `htlc_minimum_msat` and `max_cltv_expiry` as fields
  that could fingerprint padded blinded paths even after relay parameters were
  made realistic.

- Traced normal blinded-path constraint derivation through relative expiry,
  `CLTV_FAR_FAR_AWAY`, latency grace, current block height, and each hop's CLTV
  delta.

- Updated router code to derive dummy constraints from downstream
  `tlvs.payment_constraints` instead of building dummy arrays from default
  TLVs.

- Added focused unit coverage that models the same relay sequence as dummy
  hops and ordinary forward hops, then compares the constraints each position
  receives. ([Branch][dummy-follow])

### Reading recurrence as a long-lived relationship

- Studied the recurrence spec PR with attention to the places where invoice
  issuance, invoice settlement, and continuation state can diverge.

- Questioned whether stateless recurrence needs settlement proof, possibly
  through previous payment preimages, rather than only issuance-linked
  `next_state` and `prev_state`.

- Explored how recurring invoice requests can stay reachable after the
  original blinded `offer_paths` go stale.

- Revisited fixed versus payer-relative basetimes, and whether compulsory
  recurrence belongs in the protocol or should remain merchant policy.
  ([Spec][recurrence])

## Reflections

The dummy-hop work this week was useful because it made one shortcut impossible
to hide behind tests. The old complete dummy TLV could exist with constraints
that were only placeholders. Afterward the code could patch those values into
something more plausible, but that meant construction still had an impossible
middle state. The object existed before the information that made it safe to
show to forwarding validation.

Removing that middle state made the fix feel more honest. A dummy hop becomes
a complete dummy TLV only when it has downstream constraints to inherit from.
The backward walk through CLTV deltas is no longer cleanup after construction;
it is part of construction. That matters for a branch whose whole point is to
make padding disappear into the ordinary path shape. The hidden values cannot
be special and then cleaned up later.

The tests moved in the same direction. A padded path validating successfully is
only the floor. The sharper check is whether the same relay sequence produces
the same visible constraints when treated as dummy hops and when treated as
real forward hops. That comparison keeps the test near the privacy claim
instead of near the implementation detail that happened to fail.

The recurrence reading gave the week a wider version of the same discomfort
with context-free state. Continuation tokens are attractive because they let a
payee stay stateless, but recurrence is not only a repeated invoice request.
The payer may receive state for an invoice that is never paid. Blinded request
paths may go stale while the subscription is still valid. A basetime may come
from the offer or from the payer's first request. Each choice changes what the
next request has to prove.

That made the dummy-hop fix feel less isolated. In both threads, the hard part
was not adding another field or finding a nicer default. It was deciding what
context has to be present before a value can be trusted. For dummy hops, that
context is the downstream forwarding constraint. For recurrence, it may be
settlement proof, fresh request reachability, and a single clock model the rest
of the session can keep using.
