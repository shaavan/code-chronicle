## Reflection

Yesterday left the constraint problem in a useful shape, but the first code
shape still had one awkward step in it. The dummy TLVs could be created with
placeholder constraints and then made realistic afterward. That was enough to
make the values pass inspection, but it kept the construction split across two
states: first an object that should not really exist, then the object the path
actually needed.

The better version was smaller in spirit. A dummy hop should already have the
downstream constraint context when it becomes a complete `DummyTlvs`. That
made `DEFAULT_DUMMY_PAYMENT_CONSTRAINTS` the thing to remove, not improve. If
the type needs downstream state to avoid revealing itself, then a context-free
complete default is a bad convenience.

Once that fell into place, the helper split became easier to read. The
one-hop and path constructors do the backward constraint derivation directly.
Production `random_path` and deterministic test construction both pass through
that same shape. The router no longer assembles dummy TLV arrays from defaults
and later hopes the values line up; it hands the helper the downstream
`payment_constraints` and lets the dummy layers accumulate from there.

The test also tightened. I had been thinking about padded and non-padded paths
as the visible comparison, but the local invariant did not need a full onion
exercise. Modeling the same relay sequence once as dummy hops and once as
ordinary forward hops was enough. If each position derives the same
constraints in both cases, the dummy layer is using the same accounting as the
real path instead of carrying a private fingerprint in its bounds.

I liked that the final patch moved away from making bad intermediate objects
look acceptable. The privacy property is now closer to the construction path:
the downstream bound is present at the moment the dummy TLV is built. That
does not make the whole branch finished, but it removes one quiet shortcut
from the part reviewers were right to press on.
